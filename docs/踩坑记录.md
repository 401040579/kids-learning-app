## 部署 / GitHub Pages

### 1. 线上地址是自有域名，不是 github.io

站点跑在 **https://app.tao.irish/**（仓库根目录有 `CNAME` 文件）。
排查线上问题时别去访问 `401040579.github.io`。

### 2. Actions 机器人推送的提交，**会**自动触发 Pages 部署

> **实测日期**：2026-07-28

GitHub 官方文档有这么一句：

> "Commits pushed by a GitHub Actions workflow that uses the `GITHUB_TOKEN` do not trigger a GitHub Pages build."

**这句话对本仓库不成立。** 本仓库 Pages 是 legacy「Deploy from a branch」模式
（`build_type: legacy`，source = main / 根目录），实测机器人 push 后：

- 内建的 `pages-build-deployment`（event=dynamic）正常触发并部署成功
- 站点依次从 v62 → v63 → v64，两次受控测试都验证通过

**教训**：曾据那句文档加过一步显式 `POST /repos/{owner}/{repo}/pages/builds`，
结果造成**两个并发构建互相取消**，Pages API 状态显示 `errored`。已移除。

> 万一将来真的发现 bot 提交后站点不更新，手动补一次：
> ```bash
> gh api --method POST repos/401040579/kids-learning-app/pages/builds
> ```

### 3. 仓库权限默认 read，但 workflow 里可以自己提权

仓库设置 `default_workflow_permissions` 是 `read`，但在 workflow 文件里写：

```yaml
permissions:
  contents: write
```

即可获得写权限并成功 push，**不需要改仓库设置**。仓库设置只决定「默认值」不是「上限」。
（前提：main 无分支保护、无 ruleset，已确认；唯一例外是来自 fork 的 PR。）

### 4. 部署有延迟

推送到站点实际更新约 **1~2 分钟**。等待时别急着判定失败，给足 2 分钟。

## 视频模块

### 5. 公共 CORS 代理已全面失效，不要再依赖

> **实测日期**：2026-07-28

逐个测过 7 个免费公共 CORS 代理，**全部不可用**：

| 代理 | 状态 |
|---|---|
| corsproxy.io | 403 |
| api.allorigins.win | 超时 / 522 |
| api.codetabs.com | 超时 |
| thingproxy.freeboard.io | 超时 |
| api.cors.lol | 429 |
| proxy.cors.sh | 404 |

**所以：不要再引入任何运行时 CORS 代理依赖。** 需要跨域数据就在 CI 里预生成静态文件
（见 `scripts/fetch_videos.py` + `.github/workflows/update-videos.yml`）。

### 6. YouTube RSS 硬上限 15 条

`youtube.com/feeds/videos.xml?channel_id=UC...` 永远只返回**最新 15 条**，这是接口本身的限制，
不是代码问题。目标频道有 435 个视频，靠 RSS 永远拿不全。
拿全量要走播放列表页 + innertube 续页（`scripts/fetch_videos.py` 已实现）。

### 7. 「静默截断」比「抓不到」危险得多

抓取脚本最初只防「一条都没抓到」。但 YouTube 限流的典型表现是
**返回 HTTP 200 + 合法 JSON，内容却是空的**——这会让列表从 435 条悄悄变成 300 条，
校验全过、CI 全绿，还会 bump SW 版本**主动把截断结果推到所有设备**。

现在设了四道保护，任一触发都退出非 0 且**绝不覆盖已有文件**：

1. 任何频道抓到 0 条
2. 某页解析出 0 条但 YouTube 仍返回续页 token
3. 撞到 `MAX_PAGES` 上限时续页 token 还在
4. 新列表比已有文件少 10% 以上
5. （附加）`--max-pages` 局部抓取拒绝写正式文件

**原则**：宁可 CI 红一次让人来看，也不能让孩子的内容悄悄变少。

## 前端 / CSS

### 8. 新版 Chrome 把 `display: -webkit-box` 强制改写成 `flow-root`

> **实测日期**：2026-07-28

经典的两行截断写法在新版 Chrome 上失效：

```css
display: -webkit-box;
-webkit-line-clamp: 2;
-webkit-box-orient: vertical;
overflow: hidden;
```

`getComputedStyle(el).display` 返回的是 **`flow-root`**，连**内联设置也会被改写**，
于是 `line-clamp` 完全不起作用，文字被拦腰硬切。

**解法**：保留 `-webkit-box`（Safari/iOS 仍然有效，还能出省略号）+ 加标准 `line-clamp`，
再用**固定高度**兜底：

```css
height: calc(2.16rem + 8px);   /* 2 行 × line-height + 上 padding */
```

### 9. `overflow: hidden` 裁的是 **padding 盒**边缘，不是内容盒

固定高度加上后仍会看到被截断的第 3 行从底部露出来——因为内容会渲染进 `padding-bottom` 区域，
而 `overflow: hidden` 不裁那里。

**解法**：截断元素的 `padding-bottom` 必须为 **0**，底部留白挪到父元素上。
见 `.video-thumb-title` / `.video-thumb-card`。

### 10. iOS Safari 没有 `scrollend` 事件

首页分屏翻页的指示器同步不能依赖 `scrollend`（Chrome/Firefox 有，WebKit 至今没有）。
改用 `scroll` 事件 + `requestAnimationFrame` 节流，算
`Math.round(scrollLeft / clientWidth)`。见 `js/homeScreen.js`。

### 11. `scroll-snap-type: x mandatory` 容器上原生 `scrollTo({behavior:'smooth'})` 会卡死

吸附逻辑会打断平滑滚动动画，导致滚动位置纹丝不动（指示器却切了，看起来像"点了没反应"）。

**解法**：自己用 rAF 每帧直接赋值 `scrollLeft` 做缓动。见 `HomeScreen.smoothScrollTo()`。

另外：`.page` 切换用的是 `display: none`，**会丢掉 `scrollLeft`**，
所以回到首页时必须重置（`HomeScreen.onShow()`），跨页跳转要用 instant 而非 smooth。

## PWA / Service Worker

### 12. SW 是 cache-first，不 bump 版本号更新就到不了用户手上

`sw.js` 命中缓存就不走网络。所以哪怕新文件已经部署上线，**老设备上的 SW 依然一直返回旧缓存**。

任何资源变更都必须同步 bump `CACHE_NAME` 里的 `kids-learning-vNN`。
视频列表由 CI 更新，所以 CI 里也自动 bump（`.github/workflows/update-videos.yml`）。

### 13. 相对路径与绝对路径能命中同一个缓存条目

SW 预缓存的是 `/data/videos.json`，运行时 `fetch('data/videos.json')` 用的是相对路径。
**实测两者命中同一条目**（站点挂在根目录，解析结果都是
`https://app.tao.irish/data/videos.json`）。

⚠️ 但如果将来改成子路径部署，这两处必须同步改。

### 14. 从 precache 列表移除文件前，先确认文件还在

`cache.addAll()` 只要有一个 URL 404，**整个 SW 安装就失败**。
删文件时务必同步从 `sw.js` 的 `urlsToCache` 里移除。

## 调试环境

### 15. `python3 -m http.server` 会在并发请求下挂掉

本地调试时它是单线程的，本项目有 40+ 个 script 标签，浏览器并发拉取时服务进程会直接死掉。
表现为：**页面加载一半、CSS/JS 报 `ERR_CONNECTION_REFUSED`、页面完全没样式**。

看到这种现象先检查服务是否还活着，别急着怀疑代码：

```bash
lsof -nP -iTCP:8000 -sTCP:LISTEN
```

### 16. 隐藏的浏览器标签页会节流定时器

Browser pane 被隐藏时 `setTimeout` 最小间隔被钳制到 1 秒，`requestAnimationFrame` 和
`IntersectionObserver` 干脆不投递回调。写自动化验证脚本时循环次数要留余量，
别把「拿不到回调」当成代码 bug。

### 17. `display: none` 的元素会让 IntersectionObserver 误判

零尺寸矩形会被 Chrome 判成 `isIntersecting = true`，导致「滚动到底自动加载」在
用户还没进页面时就自我级联触发（实测一进探索页就已经渲染了 96 张卡而非 24 张）。

**解法**：回调里加 `if (entry.boundingClientRect.height <= 0) continue;`

## AI 聊天 / 语音

### 18. Puter.js 会弹**英文服务条款同意框**，且必须点了才能用

> **实测日期**：2026-07-28（两次独立复现，含截图）

`puter.ai.txt2speech()` 和 `puter.ai.chat()` 在用户未授权时，都会弹出一个
**全英文的 Terms of Service / Privacy Policy 同意框**（Continue / Cancel），
并且**挂起等待用户点击**（实测卡 7~9 秒）。给 5-7 岁的中国孩子看这个，等于功能不可用。

⚠️ 网上/文档里说「Puter 静默创建匿名账号、无弹窗」是**不准确的**——那是在已授权过的
浏览器环境里测的结果。首次访问一定会弹。

`puter.auth.isSignedIn()` 在未授权时返回 `false`，可以用它提前判断，
不要用 `typeof puter !== 'undefined' && puter.ai.txt2speech` ——
那只检查 API **存在**，未登录时同样为 true。

统一入口已封装在 `js/puterTTS.js`：先探测、加超时、失败后本会话不再重试。

### 19. WebLLM 的模型缓存在 Cache API，不在 IndexedDB

`checkModelCached()` 原来查 `indexedDB.databases()`，恒为 `false`。
WebLLM 默认 `cacheBackend: "cache"`，scope 名是 `webllm/model`、`webllm/wasm`、
`webllm/config`。查错地方的后果：模型明明已在本地，孩子每次点开 AI 聊天
还是被「需要下载 350MB」的确认框吓一次。

### 20. 本地小模型（0.5B）会自信地教孩子错误知识

实测 `Qwen2.5-0.5B-Instruct-q4f16_1-MLC` 的表现：

| 测试 | 结果 |
|---|---|
| 「长颈鹿有多高？」问 4 次 | 19米 / 13米 / 10米 / 避答（正确约 4.5 米），**每次都不同、每次都错** |
| 「为什么小鸟会飞？」 | 「因为它们会飞。」（循环废话） |
| 简单加减法 | 约 7/8 正确，错的那次「9减4」答 8 |
| 乱按键盘「阿斯顿撒的发」 | 编造「阿斯顿撒的头发是蓝色的」 |
| 系统提示词遵守 | 基本无视——不用 emoji、不说鼓励语、超出句数限制、敏感话题不引导问爸妈 |

**结论**：0.5B 档位的设计用途是补全和分类，不是自由对话。对**学习类**应用来说，
不稳定的错误事实比没有 AI 更糟。

### 21. iOS 上跑本地大模型基本不现实

- WebGPU 直到 **Safari 26.0**（2025-09）才默认开启，之前的 iPhone/iPad 上
  `navigator.gpu` 是 undefined，AI 入口根本打不开
- iOS 给单个网页的内存额度远低于模型需求（社区实测软阈值可低至 500MB，
  硬线约 1.5~2GB），WebLLM 维护者对 iOS 崩溃的官方回应是
  **"I do not believe this can be fixed on our side."**
  （https://github.com/mlc-ai/web-llm/issues/753）
- 当前 0.5B 模型声明 `vram_required_MB: 945` 已是擦边；换更强的 0.8B（1629MB）
  在 iPhone 上只会从「偶尔能跑」变成「一定跑不了」

**所以**：不要试图靠「换个更大的本地模型」来改善 iPad/iPhone 上的 AI 体验，
方向就是错的。

### 22. 验证前端改动时，Service Worker 和浏览器缓存会反复骗你

调试期间多次出现「代码明明改了但页面行为没变」，依次踩了三层缓存：

1. **Service Worker**（cache-first）——服务器发 `Cache-Control: no-store` 也拦不住，
   必须 `getRegistrations()` 逐个 `unregister()` + `caches.delete()`
2. **浏览器 HTTP 启发式缓存**——`python3 -m http.server` 不发 `Cache-Control`，
   浏览器会自作主张缓存 JS/CSS，`location.reload()` 和 navigate 的 force 都不一定能绕过
3. **已缓存条目不会因为服务器后来加了 no-store 头而失效**

**可靠做法**：用带 no-store 头的服务（见 `/tmp/nocache_server.py` 的写法），
并且**换一个该浏览器从未访问过的端口**。判断代码是否真的加载了，
不要看行为，直接查 `SomeObject.someFn.toString().includes('新代码特征')`。

## GitHub 配额 / CI 成本

### 23. 每次 Pages 部署都打包整站，仓库里的大文件会把 Actions 存储配额撑爆

> **实测日期**：2026-07-29

**现象**：一次会话里推了十来次，就产生了 **8 个 `github-pages` artifact，合计 1.2 GB**，
把免费账户 500 MB 的 Actions 存储配额撑到 2.4 倍。

**根因链条**：
1. legacy「Deploy from a branch」模式下，每次部署都由内建的 `pages-build-deployment`
   把**整个工作区打包成一个 artifact**
2. 仓库里 `music/` 有 158 MB 的 MP3（两个各长达 2 小时），所以单个 artifact 就是 **155 MB**
3. artifact 默认保留 **90 天**

于是稳态占用 = 155 MB × 每天部署次数 × 90 天。哪怕每天只部署一次，
峰值也有 **≈14 GB，是配额的 28 倍**。

**重要**：Actions 存储按**账户共享配额**计费，**和仓库是否公开无关**。
「公开仓库免费」指的是 **Actions 分钟数**，不含存储。这点很容易搞混。

**解法（按有效性排序）**：

1. **把 artifact 保留期从 90 天改成 1 天** —— 决定性的一项，峰值直接从 14 GB 降到 155 MB。
   artifact 只是构建记录，站点上线后就没用了，缩短无实质损失。
   ```bash
   # 查看
   gh api /repos/401040579/kids-learning-app/actions/permissions/artifact-and-log-retention
   # 设置（实测会**追溯**修改已有 artifact 的过期时间，不只对新的生效）
   gh api -X PUT /repos/401040579/kids-learning-app/actions/permissions/artifact-and-log-retention -F days=1
   ```
   （UI 路径：Settings → Actions → General → Artifact and log retention）

2. **减小仓库里的大文件** —— artifact 大小 = 工作区大小。
   `music/` 的 158 MB 若压成 5 分钟单声道循环（需同时在代码里开 `loop`），
   可降到约 9 MB，artifact 随之降到约 12 MB。
   附带好处：孩子听一次睡眠音乐目前要下 **55 MB**，压缩后只要 1.8 MB。
   *（2026-07 暂未执行，音乐保持原样。）*

**手动清理已有 artifact**：
```bash
gh api '/repos/401040579/kids-learning-app/actions/artifacts?per_page=100' \
  --jq '.artifacts[] | select(.expired==false) | .id' \
  | tail -n +2 \
  | xargs -I{} gh api -X DELETE /repos/401040579/kids-learning-app/actions/artifacts/{}
```
（`tail -n +2` 保留最新一个。删 artifact **不会**让站点下线——站点已由 CDN 提供，
artifact 只是构建产物记录。删之前确认 `gh api .../pages/builds/latest` 的 status 是 `built`。）

**给以后的提醒**：往仓库里加大文件（音视频、数据集）前先想一下，
它会乘以「部署次数 × 保留天数」变成存储账单。
