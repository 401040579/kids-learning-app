## 1. YouTube 播放器没有点击遮罩，孩子点一下视频标题就能跳出应用、进入完整无限制的 YouTube

- **位置**：`js/app.js`:407
- **分类**：child-safety

**孩子/家长会遇到什么**

孩子在「探索视频」点开白名单频道的视频，播放中手指碰到画面顶部的标题（视频区上方约 1/6 的高度，误触概率很高）→ 系统跳到 Safari 打开 youtube.com 完整站点。因为是「添加到主屏幕」的 standalone PWA，孩子跳出去后**没有返回按钮**，只能靠 App 切换器回来；而 YouTube 站内推荐流、搜索框、评论区、自动播放全开放。整个 videoWhitelist.js + CI 预生成 data/videos.json 的白名单体系被一次误触完全绕过。

**建议修法**

两处都要补：
1) 加一层透明点击盾牌盖住标题条区域（不影响中间播放/暂停和底部进度条）：
```html
<!-- index.html 的 .video-container 内，#video-player 之后 -->
<div class="video-tap-shield"></div>
```
```css
.video-tap-shield{position:absolute;top:0;left:0;right:0;height:60px;z-index:5;background:transparent;}
```
2) 降级 iframe 加 sandbox，物理禁止弹窗和顶层跳转（故意不给 allow-popups / allow-top-navigation）：
```js
' sandbox="allow-scripts allow-same-origin allow-presentation"' +
```
3) playerVars 补 `modestbranding: 1, iv_load_policy: 3, disablekb: 1`。

**验证环节的补充/纠正**

建议的修法方向对，但**第 1 条不够、第 3 条基本无效**，照抄会留下逃逸口：

1) 顶部 60px 盾牌**堵不住全部出口**（已实测）：右下角 "Watch on YouTube" logo 是独立链接，点了照样新开 youtube.com；左上角频道头像/频道名指向频道页；左下角还有 Share 按钮。只盖顶部等于修了一半。
   → 可行做法二选一：
   a. 顶部条 + 右下角一起盖（两块透明盾，右下角至少 90x40），中间和进度条留空；
   b. 更稳：整块透明盾覆盖 #video-player，播放/暂停用自家大按钮调 `ytPlayer.playVideo()/pauseVideo()`（IFrame API 已经在用了，成本不高），孩子本来也不需要拖进度条。
   注意 `.video-close` 是 z-index:10，盾牌用 z-index:5 不会挡住关闭按钮，这点没问题。

2) `sandbox` 那条**实测可行**：我用 `sandbox="allow-scripts allow-same-origin allow-presentation"` 加在与 app.js:446-448 完全相同的裸 iframe 上，视频正常加载播放（截图确认），同时因为没给 allow-popups / allow-top-navigation，链接点了不会跳出。可以直接加。
   但要清楚：这只救得了**降级路径**。主路径的 iframe 是 YT API 自己创建的，拿不到 sandbox 属性（事后 setAttribute 也要重载才生效），所以主路径必须靠盾牌/controls。

3) `modestbranding: 1` 是**废弃参数**（YouTube 2023-08 起不再生效），我在默认参数下的实测里 YouTube logo 照常显示；`iv_load_policy:3`、`disablekb:1` 无害但也不解决外链。这三项不要当成修复手段。
   真正有效的单参数是 `controls: 0`：加上后 CDP 读到的 iframe a11y 树里**一条链接都没有**（只剩一个 "Show player controls" 节点），手机尺寸下点画面也没唤出标题条。代价是没有播放/暂停 UI——iOS 上带声音的 autoplay 会被拦，必须有一次用户手势，所以用 controls:0 的话**一定要同时用 IFrame API 做自家的播放/暂停按钮**，否则会变成「点开视频黑屏不动」的新 bug。

4) 顺带两个可以一起修的相邻问题（不必单开）：CLAUDE.md 写的 youtube-nocookie.com 与代码里的 www.youtube.com/embed 不一致；播放器里的 "More videos" 按钮在视频没结束时就能拉出推荐内容，ENDED 遮罩管不到它——上面的 b 方案（整块盾牌）能顺手把它也堵掉。

## 2. 油漆桶填色用字符串 Set + 数组栈做 BFS，全屏填一次要吃掉 350MB 内存、卡死数秒

- **位置**：`js/drawing.js`:768
- **分类**：内存/算法

**孩子/家长会遇到什么**

孩子在画画创作里选「油漆桶」，点在还没画东西的白色背景上（这是 5-7 岁最常见的操作）→ 界面完全冻结 5~10 秒，手指怎么点都没反应；iOS Safari 给单个页面的内存额度远低于 443MB，大概率直接白屏/闪退回主屏，正在画的画全丢。画得越空、要填的面积越大，越容易崩。

**建议修法**

两处改，都不影响功能：
1. visited 换成定长字节数组，内存从 ~350MB 降到 W*H 字节（1.5MB）：
```js
const visited = new Uint8Array(width * height);
// ...
const pi = cy * width + cx;
if (visited[pi]) continue;
visited[pi] = 1;
```
2. 栈别存 `[x,y]` 小数组，存一个整数索引 `cy*width+cx`，出栈时 `cx = i % width; cy = (i/width)|0`；并且入栈前先判边界。
再进一步可以换成扫描线（scanline）填充，入栈量能再降一个数量级。

**验证环节的补充/纠正**

建议的修法方向正确，但**有一个会引入新 bug 的坑必须提醒**，另外我实测了修复效果：

【坑：Uint8Array 替换 Set 时，边界检查必须提前】
现在的代码顺序是 L810 `visited.has(key)` 在前、L811 边界检查在后。字符串 key 时这么写是安全的（"-1,5" 和 "1535,4" 是不同 key）。但换成扁平索引 `pi = cy*width+cx` 后，cx=-1、cy=5 会算出 `pi = 5*width-1`，那是**第 4 行最后一个像素的合法下标**——会发生行间环绕，把上一行行尾的像素误判成已访问，导致左右边缘出现填不满的竖条纹。
所以必须把边界判断挪到算 pi 之前（或者像建议 2 那样入栈前就判边界），不能只做 Set→Uint8Array 的原地替换。

【实测修复效果（同机同 node，扫描线版）】
- 1536×1024：1821ms → **22ms**（83x），heapUsed 213MB → **3.4MB**，rss 323MB → 46MB，peakStack 1,966,468 → **2**
- 1107×1500：1969ms → 25ms，heapUsed 400MB → 3.3MB
- 1968×2200：5777ms → 53ms，heapUsed 1067MB → 3.3MB
栈用 `new Int32Array(width*height)` 定长即可，扫描线版每行只入栈一次，不会溢出。

【功能等价性我验证过】
在 200×150 画布上随机撒 40 个黑色圆形障碍，8 个随机种子 × 5 个不同起点 = 40 组用例，原算法与扫描线版输出的 ImageData **逐字节完全一致**（含从障碍内部起点、四角起点的退化情况）。tolerance=32 的容差语义、以及「填充色与目标色相近时靠 visited 防死循环」的行为都保留了（扫描线版同样先查 visited 再查 match）。

【两点顺带说明，不影响本条修复】
1. L790 提前返回只比了 RGB 没比 alpha，调色板里有 '#FFFFFF'（js/drawing.js:56），孩子选白色点白底会命中这个提前返回，不会触发慢路径——这是现状唯一的「运气好」路径，不能当作缓解措施。
2. floodFill 结尾 L832 还会调一次 `saveState()`（内部是 toDataURL 全尺寸 PNG，history 上限 20），这是另一笔开销，本条修完后它会变成新的耗时大头，但属于独立问题，不要混进这次改动。

## 3. 20 幅画作以 base64 存 localStorage，第 3~4 幅就撑爆 iOS 5MB 配额，之后全站 29 个存档点一起失效

- **位置**：`js/drawing.js`:649
- **分类**：存储配额

**孩子/家长会遇到什么**

两级伤害：
1. 孩子画到第 4 幅点「保存」→ QuotaExceededError 从 saveToGallery 抛出，直接中断 saveArtwork()，后面的 `alert('画作已保存！')`、`RewardSystem.addPoints(10)`、`ParentNotify.send()` 全都不执行。孩子看到的是：点了保存，**什么都没发生**，也没加分，家长手机也收不到通知。
2. 更糟的是配额是按整个域算的。一旦被画作占满，之后每一次答对题加星星、解锁成就、每日签到、错题本记录……29 处 setItem 全部开始抛异常且无人接住 → 孩子的学习进度从此再也存不下来，重启 app 全部回到爆配额前的状态。

**建议修法**

1. 画作别存 localStorage。最省事的两条路：
   - 存前先降尺寸+转 JPEG：`canvas.toDataURL('image/jpeg', 0.7)` 并限宽 800px，单幅能压到 60~120KB；同时把 `slice(0, 20)` 改成 `slice(0, 5)`。
   - 或者改用 IndexedDB 存 Blob（`canvas.toBlob`），配额是 localStorage 的几百倍。
2. 无论怎么改，saveToGallery 必须包 try/catch，捕获后弹「相册满啦，先删几张老画吧」并自动丢弃最旧的一张重试。
3. 建一个全局 `safeSetItem(key, val)` 包一层 try/catch，把那 30 处裸调用统一换掉（sed 就能做），避免一处爆配额拖垮全部模块。

**验证环节的补充/纠正**

报告的修法方向对，但因为「artworkGallery 没有任何读取方」这个事实，优先级要调整：

**首选（最省事且最正确）：直接删掉这次写入，别做压缩。**
- 删 `js/drawing.js:627` 的 `this.saveToGallery(dataUrl);` 和 `649-659` 的函数本身。
- 孩子的画在 `drawing.js:620-624` 已经通过 `link.download` + `link.click()` 存进系统「文件/照片」了，localStorage 那份纯属冗余且无人读。
- **必须配一次性清理**：在 app 启动处加 `localStorage.removeItem('artworkGallery')`，把已经被占掉的最多 5 MB 还回去。否则已经踩坑的设备光删代码不会自愈。
- 记得 bump `sw.js` 版本号（踩坑记录 #12），否则改动到不了已装 PWA 的手机上。

**如果家长确实想要「作品集」页面**（那才需要压缩）：
- 必须先建 UI，否则压缩仍是给没人看的数据省空间。
- 实测 iPad 画布 1960×1420 缩到 800px 宽 + JPEG q0.7 ≈ 120~240 KB chars，`slice(0,5)` 后 ≈ 1 MB，**仍占掉 20% 全域配额**。所以真要做相册，建议直接 `canvas.toBlob()` 存 IndexedDB，别碰 localStorage。
- 注意 JPEG 的一个副作用：`clear()` 在暗色模式下填的是 `#1a1a2e`（drawing.js:550），霓虹发光笔刷（`drawMagicLine` 的 `shadowBlur`）在深色底上做 q0.7 JPEG 会有明显色带；真要用 JPEG 建议 q0.85。

**try/catch 位置要讲究（报告没说清）**：光在 `saveToGallery` 内部包 try/catch 不够，关键是保证 `alert('画作已保存！')` / `RewardSystem.addPoints(10)` / `ParentNotify.send()` 照常执行——即把 `saveArtwork` 里第 627 行那次调用包起来。这样最坏情况从「孩子点了保存像死机」降级成「画照常下载、照常加分、只是没进那个没人看的相册」。

**全局 safeSetItem 别无脑 sed**：报告建议 sed 批量替换 30 处裸调用，但静默吞掉 QuotaExceededError 会让错题本、家庭积分榜静默丢数据，比抛异常更难排查。若要做，safeSetItem 失败时至少 `console.warn` + 走 `Analytics` 上报，让家长事后能发现。另外这 30 处的优先级远低于删掉画作写入——实测证明只要画作不占坑，其余 28 个键加起来离 5 MB 还很远。

## 4. kidsLearningData 被两条路径同时写：RewardSystem 的内存快照会回写覆盖直写结果，孩子的积分会当着他的面变少

- **位置**：`js/rewards.js`:110
- **分类**：数据一致性/状态管理

**孩子/家长会遇到什么**

孩子做完一整个科学主题，弹窗写着「+100 积分奖励！全对太棒了！🎊」，首页总分从 415 跳到 515。他高高兴兴去做一道数学题（+10 分），总分立刻变成 425——凭空少了 90 分，而且是永久性的。另外每答对一道科学题，刚存进去的完成记录立刻被抹掉，所以科学主题列表上的进度条「0/10」几乎永远不动（只有答错的题会留下来），孩子会反复被推去做同一批题。

**建议修法**

统一成一条写入路径。最小改动：让 B 类直写走 RewardSystem，而不是自己碰 localStorage。
```js
// app.js showScienceComplete 里
RewardSystem.data.totalScore += bonusPoints;
RewardSystem.data.tasksDone += 1;
RewardSystem.saveData();
RewardSystem.updateDisplay();
```
saveScienceProgress 同理，改成写 `RewardSystem.data.scienceProgress` 再 `RewardSystem.saveData()`。若不想动结构，退而求其次：把 `RewardSystem.saveData()` 改成读-改-写合并（读出最新 LS，只覆盖自己负责的字段），避免整对象覆盖。

**验证环节的补充/纠正**

建议的修法方向正确，但有三处补充，直接照抄会留坑：

**(a) 还有第三个写入点必须一起改**：js/app.js:907-919 `loadScienceProgress()` 也在直写 LS，而且调用顺序是 `RewardSystem.init()`（app.js:90，此时已 loadData 快照）→ `initScience()`（app.js:134）→ `loadScienceProgress()` 写 LS。老用户第一次进来时它给 LS 补上 `scienceProgress` 结构，但 `RewardSystem.data` 里没有这个键，下一次 addPoints 直接把整个键删掉。只改 `saveScienceProgress` + `showScienceComplete` 两处不够。

**(b) 退而求其次的「合并式 saveData」不能用对象展开写**：因为 `loadData()` 是 `this.data = JSON.parse(saved)` 整对象接管，`this.data` 里**本身就带着一份陈旧的 scienceProgress**。写成 `{...JSON.parse(ls), ...this.data}` 完全无效——陈旧值仍然赢。必须显式白名单只回写 RewardSystem 自己拥有的 7 个字段：
```js
saveData() {
  const cur = JSON.parse(localStorage.getItem('kidsLearningData') || '{}');
  ['totalScore','tasksDone','mathCorrect','mathStreak','englishCorrect','chineseCorrect','scienceCorrect']
    .forEach(k => { cur[k] = this.data[k]; });
  localStorage.setItem('kidsLearningData', JSON.stringify(cur));
}
```
这一处改动能一次性覆盖 rewards.js 里全部 4 个 `this.saveData()` 调用点（147/177/220/345）以及 dailyCheckin/learningPet 走的同一条路径，是改动面最小、最符合「改一个地方就生效」偏好的方案。注意 `loadData()` 也要相应只取这 7 个字段，否则 `this.data` 仍会挂着陈旧的 scienceProgress 副本（虽然不再被写出去，但容易误导后续代码）。

**(c) 若采纳原方案（B 类改走 RewardSystem）**，`showScienceComplete` 里除了 `RewardSystem.saveData()` 还必须调 `RewardSystem.updateDisplay()`，不能保留原来的 `document.getElementById('total-score').textContent = ...` 直写，否则 DOM 和 data 还是会再次分叉。另外 `getScienceProgress()`（app.js:923-937）继续读 LS 是安全的（saveData 会同步 LS），可以不动。

**(d) 修完需要 bump sw.js 版本号**（当前 v50），否则老用户拿不到修复——踩坑记录第 12 条已说明 SW 是 cache-first。

## 5. iPhone 横屏玩打地鼠时最下面一排 3 个洞完全在屏幕外且划不到

- **位置**：`css/style.css`:14145
- **分类**：orientation-layout

**孩子/家长会遇到什么**

孩子把 iPhone 横过来玩打地鼠（躺着玩、或者手机放桌上时非常常见），九宫格最下面一排的 3 个洞在屏幕外面。地鼠会照常从那 3 个洞冒出来又缩回去，孩子既看不见也点不到，`this.misses++` 照记——分数被硬生生扣掉三分之一，孩子会以为是自己太慢。

**建议修法**

给 `.mole-hole` 改成按可用空间自适应，而不是写死 90px：
```css
.mole-grid { 
  grid-template-columns: repeat(3, 1fr);
  width: min(340px, 90vw, 70vh);   /* 横屏时用 vh 约束 */
  aspect-ratio: 1;
}
.mole-hole { width: 100%; height: 100%; }  /* 去掉 90px/70px 两处写死 */
```
抓星星、颜色闪电也在同一个 overflow:hidden 容器里，改完顺手在横屏下过一遍。

**验证环节的补充/纠正**

**建议的修法我实际注入 CSS 跑了一遍，它修不好这个 bug，还引入新 bug，不要照抄。**

实测（667x330 下注入 `.mole-grid{width:min(340px,90vw,70vh);aspect-ratio:1}` + `.mole-hole{width:100%;height:100%}`）：

1. **仍然溢出**。`70vh` 完全没有扣掉 grid 上方被 header 占掉的 114.5px。vh=330 时 70vh=231，114.5+231=345.5 > 330，第三排照样被切。截图确认底排还是缺一块。

2. **iOS 上更糟**。真机 Safari 的 `vh` 解析的是「大视口」（地址栏收起时的高度），不是当前可见高度，所以 70vh 在真机上比我测的还要高估。要用 `dvh`，或者干脆别用视口单位——沿 flex 链加 `min-height:0` 然后 `height:min(100%,340px)` 更稳。

3. **地鼠会被砍头**。`.mole{font-size:3.5rem}`（style.css:14501）和 `.mole.active{bottom:15px}`（14508-14510）也是写死的 px，建议里没动。hole 缩到我实测的 53.7px 时，地鼠 emoji 盒子仍是 73.5px 高，顶部 34.8px 被 `.mole-hole{overflow:hidden}` 裁掉——截图里地鼠耳朵和头顶整个没了。任何缩放方案必须让 `.mole` 的 font-size 和两处 `bottom`（-60px / 15px）跟着一起缩，比如在 `.mole-hole` 上设 font-size 然后内部全用 em。

4. **`.mole-hole{height:100%}` 写法脆弱**。`.mole-grid` 没有显式 `grid-template-rows`，百分比高度对着 auto 行解析是循环依赖，各浏览器行为不保证（我这次侥幸算对了）。应该补 `grid-template-rows:repeat(3,1fr)`，然后把 `.mole-hole` 的 width/height 直接删掉，靠 grid 默认 stretch 填满。

**更符合「改一个地方就生效」的方向**：加一条按高度而非宽度卡的横屏媒体查询，例如 `@media (orientation:landscape) and (max-height:500px)`，在里面同时压缩 header 和等比缩 hole/font-size/bottom。注意 header 那一坨（.reaction-game-area 的 15px padding + header 本体 + 15px margin）实测就吃掉 114.5px，330px 视口下不压 header 光缩洞是不够的。改完请在 667x330 而不是 667x375 下验证，并顺带过一遍 colorFlash 和 catchStars——它们是同一个根因，且比打地鼠更严重。

## 6. js.puter.com 在每次打开应用时同步加载，能读到孩子照片和家长的 Bark 推送 URL——而按踩坑记录 #18 它实际上永远用不上

- **位置**：`index.html`:2840
- **分类**：supply-chain

**孩子/家长会遇到什么**

puter.com 一旦被入侵或改动脚本内容（无 SRI，改了也发现不了），攻击者能拿到孩子的照片和姓名，并且能用家长的 Bark URL 往爸妈手机推任意内容——包括伪造的「孩子按了紧急求助」。日常层面还有代价：这个同步 script 挂在 40 多个业务脚本前面，网络差或 js.puter.com 不可达时会阻塞整个应用的 JS 加载，孩子看到的是长时间白屏。

**建议修法**

改成按需加载，平时根本不引入。删掉 index.html:2840 的 script 标签，在 js/puterTTS.js 里加懒加载：
```js
_loading: null,
async ensureLoaded() {
  if (window.puter) return true;
  if (this._blocked) return false;
  this._loading = this._loading || new Promise(res => {
    const s = document.createElement('script');
    s.src = 'https://js.puter.com/v2/';
    s.onload = () => res(true); s.onerror = () => res(false);
    document.head.appendChild(s);
  });
  return this._loading;
}
```
更干脆、也更符合踩坑 #18 结论的做法：**直接删掉 Puter TTS**，只保留 Web Speech API 降级路径——实测有 18 个中文语音可选，完全离线、零第三方依赖。

**验证环节的补充/纠正**

原报告给的懒加载补丁是错的，别照抄：

(a) 那段 `ensureLoaded()` 是死代码。4 个调用方都是同步调用 `if (PuterTTS.available())`（aiChat.js:645、pictureBook.js:555、writing.js:824、songPractice.js:245），没有一处 await ensureLoaded()，加了也永远不会被触发。
(b) 就算改造调用方去 await 它，上面证明的死锁依然在——脚本加载完 authToken 仍是 null，available() 仍是 false。懒加载在这里买不到任何东西，只是把 352KB 从「每次启动」挪到「永远不加载」，纯属绕远路。

推荐的最小改动（我已验证行为完全等价，符合「改一处就生效」的偏好）：
1. 删掉 index.html:2840 这一行，只删这一行。
   之后 `typeof puter === 'undefined'` 成立 → puterTTS.js:26 直接 return false → 4 个调用方全部落到已有的 Web Speech 分支。这些 else 分支我逐个读过，都存在且完整：aiChat.js:654 speakWithWebSpeech(text)、pictureBook.js:574-576、writing.js:827 `else if ('speechSynthesis' in window)`、songPractice.js:258-260。孩子侧听到的声音和今天一模一样（今天本来就是 Web Speech）。
2. 必须 bump sw.js 的 CACHE_NAME（当前 v67），否则改动到不了已安装 PWA 的设备。
3. sw.js:18 的 `'/js/puterTTS.js'` **不用动**，puterTTS.js 保留即可（它此时是一个恒返回 false 的空壳，留着不影响功能，也省得改 4 个文件）。js.puter.com 是跨域，SW 从来没缓存过它——sw.js:109 `if (url.origin !== self.location.origin) return;` 直接放行，所以缓存清单无需调整。

想更彻底（可选，非必需）：删掉 js/puterTTS.js + sw.js:18 + 4 个调用点的 PuterTTS 分支，只留 Web Speech。功能等价，但要动 6 个文件，收益只是少 55 行代码，按「不接受重型重构」的约束，不如先做第 1 步。

顺带（不属于本条发现，可另开一条 triage）：index.html:2843 的 hanzi-writer 同样是跨域同步脚本、无 defer、无 SRI，只是它确实被 writing.js 用到。若在意启动阻塞和供应链，可考虑把它 self-host 到 /js/vendor/ 下（约 60KB，一次性下载，同时能进 SW 缓存实现真离线），这比给它加 SRI 更划算。

## 7. 两个第三方 CDN 同步 script 卡在所有本地 JS 前面，占掉首屏 57% 的时间，且离线时必然失败

- **位置**：`index.html`:2840
- **分类**：首屏加载

**孩子/家长会遇到什么**

孩子点开主屏图标 → 先看到「欢迎小朋友!」和 4 个分类 tab，**中间一片空白、一个功能图标都没有**，要等 puter.js 从境外 CDN 回来才刷出来。在 Mac + 本地服务器上是 0.3 秒；孩子的 iPad 走家里 wifi/4G 拉 js.puter.com，几秒起步；弱信号或 puter.com 被墙时会一直等到 TCP 超时（iOS 上可达几十秒），孩子会以为 app 坏了反复退出重进。

而且按踩坑记录 #18，puter.js 在未授权时只会弹英文条款框然后降级 —— 也就是说这 376ms 是为一个大概率用不上的能力付的。

**建议修法**

零重构，改 index.html 就行：
1. 给 **所有** `<script src=...>` 加 `defer`（`defer` 保证按书写顺序执行，locales 依赖 i18n.js 的顺序不受影响）。这样解析器不再被任何脚本阻塞，本地 JS 206ms 就能开始跑。
2. 更好的是把这两个第三方标签直接删掉，改成用到时再注入：
   - hanzi-writer 只有 writing.js 用（writing.js:164 才检查 `typeof HanziWriter`），在 `openWriting()` 里动态 `document.createElement('script')` 注入即可，它本来就已经在从同一个 CDN 拉汉字数据了。
   - puter.js 只有 puterTTS.js 用，同理在第一次真正要 TTS 时注入。
3. 顺带给这两个域名加 `<link rel="preconnect">`（如果保留的话）。

**验证环节的补充/纠正**

原建议第 1 条（全部加 defer）已实测无效，请勿采用。按可行性排序：

1）**puter.js：直接删掉 index.html:2840 这一行**（零风险，一行改动）。
   全仓库只有 puterTTS.js 用 `puter`。删掉后 `typeof puter === 'undefined'` → `PuterTTS.available()` 恒为 false → writing.js:824 / aiChat.js:645 / songPractice.js:245 / pictureBook.js:555 四个调用点全部走已有的 Web Speech 降级分支。我在 nocdn 变体里实测过：`PuterTTS.available() === false`、首页图标正常渲染、DCL 365ms、无报错。按踩坑记录 #18，未登录本来就是这个结果，所以功能上没有任何损失。
   （若将来家长真想用 Puter 神经语音，再在 PuterTTS.speak 第一次被调用时动态注入即可，不必开机就付这个钱。）

2）**hanzi-writer：优先「本地化 vendoring」而不是 lazy inject**。
   它只有 11KB gzip，直接下载到 `js/vendor/hanzi-writer.min.js`，index.html 改成同源引用，并加进 sw.js 的 urlsToCache + bump CACHE_NAME。这样既去掉跨域阻塞，又顺带让书写模块真正离线可用（现在离线只靠浏览器 HTTP 缓存赌运气）。
   ⚠️ 按踩坑记录 #14，必须**先确认文件已提交存在**再往 urlsToCache 里加，否则 `cache.addAll()` 一个 404 会让整个 SW 安装失败。

3）**如果只想改 index.html、一个字符都不想多动：给这两个 tag 加 `async` 而不是 `defer`。**
   我实测了 asynchang 变体（两个第三方 tag 加 async，puter 换成 sleep 8s 的脚本）：`domContentLoadedEventEnd = 232ms`、FCP 208ms、`#home-pager` 4 个子元素全部渲染，而那个慢脚本 8210ms 才回来——完全不再阻塞。async 在这里安全，因为两个库都没有互相依赖，消费方都是在用户点击后才用到、且都做了 typeof 守卫。

4）preconnect 那条：如果按方案 1+2 执行，两个域名都没了，preconnect 就不需要了；只有在选方案 3 保留 CDN 时才有意义。

## 8. 首页根本用不到的大游戏模块全部同步加载，parkWallpaper 一个就 135KB

- **位置**：`index.html`:2892
- **分类**：首屏加载

**孩子/家长会遇到什么**

孩子只想做两道算术题，也要先下载并解析 135KB 的魔法公园物理引擎和 80KB 的布娃娃引擎。iPad 上这些解析时间累加起来就是开屏那段空白。每天 CACHE_NAME bump 之后这 2MB 还要整个重下一遍（见另一条 sw.js 的发现）。

**建议修法**

不需要打包工具，加一个 12 行的按需加载器就够，符合「改一个地方就生效」：
```js
// js/app.js 里加
const _loaded = {};
function lazyScript(src) {
  if (_loaded[src]) return _loaded[src];
  return _loaded[src] = new Promise((res, rej) => {
    const s = document.createElement('script');
    s.src = src; s.onload = res; s.onerror = rej;
    document.head.appendChild(s);
  });
}
```
然后把 index.html 里那几个 script 标签删掉，对应的全局入口函数改成：
```js
function showParkWallpaper() {
  lazyScript('js/parkWallpaper.js').then(() => ParkWallpaper.show());
}
```
sw.js 的 urlsToCache **保持不动**（这些文件仍然预缓存），所以离线首次点进去也能秒开，只是不再阻塞首屏。

另外无论做不做懒加载，先给所有 `<script>` 加 `defer` 是零风险的（defer 保序），能立刻解除解析器阻塞。

**验证环节的补充/纠正**

【严重度上调 P2 → P1 的理由】不是抽象性能指标。首页图标区在 JS 跑完前是空的（index.html:308 空 div + app.js:75 才渲染），孩子面对的是"一个图标都没有的首页"。叠加每日 CACHE_NAME bump 导致的冷缓存全量重下（v69 且 CI 天天跑），最坏情况是每天早上第一次打开都要盯着空屏幕好几秒 —— 5 岁孩子的反应是乱点或退出，不是等待。不到 P0 是因为最终能恢复、没有数据损坏。

【修法必须修正的三处】
1. 懒加载入口不能只 `.then(() => Mod.show())`。对 8 个有 init 的模块必须写成 `.then(() => { Mod.init(); Mod.show(); })`，同时把 init() 做成幂等（memoryGame/pictureBook/pronunciation/familyPK/englishBoost/birthdayParty/toothFairy 的 init 只是 loadX()，天然幂等；choreTracker 的 init 会写 localStorage，需要加一个 `if (this._inited) return;`）。并且要**同步删掉 js/app.js:97-126 里对应的 typeof 守卫调用**，否则那几行等于白留。
2. 第一批只动这 4 个真正零依赖的，风险最低、收益最集中：parkWallpaper.js(135KB) + music.js(30KB) + writing.js(25KB) + drawing.js(36KB) ≈ 226KB raw。单 parkWallpaper 一个就占了全站本地 JS 的 11%。pictureBook.js / pronunciation.js 建议**先不动**，除非先把 app.js:2795-2860 那 8 个重复定义清理掉（原文的 B 类顺序反转问题）。
3. 如果只想做一件成本最低的事，优先级应该是给两个 CDN script 加 defer/async，而不是给本地 script 加 defer。puterTTS.js 本来就设计成 Puter 缺席时降级 Web Speech，HanziWriter 也只在 writing.js 点进去后才用 —— 但这一条我没有实际验证 puterTTS.js 对"晚到的 window.puter"的处理，改之前要单独确认一次，别当成免费午餐。

【不要写进收益的】离线首次点入依然要读 SW 缓存（sw.js 已预缓存，成立）；但"减少每日重下流量"不成立，urlsToCache 不变就一个字节都没省。

## 9. 「强制刷新」「家长设置」「紧急求助」跟玩具图标混在一起，孩子一点就中

- **位置**：`index.html`:682
- **分类**：信息架构

**孩子/家长会遇到什么**

孩子在「我的信息」页乱点，点到 🔄 又点了「确定」（对话框上只有两个按钮，五岁孩子一半概率点右边），Service Worker 和所有缓存被删光。如果这时候在车上/飞机上没网，页面 reload 后直接白屏，整个 App 打不开。同理 🆘 点两下就给爸妈手机推一条紧急求助；家长设置里删掉 Bark URL 后，真正需要求助时反而发不出去。

**建议修法**

最省事：把「家长设置」和「强制刷新」挪到一个简单的家长闸门后面（长按 3 秒进入，或问一道两位数加法，比如「38+45=?」——学龄前答不出、家长秒答，不需要密码不需要后端）。紧急求助保留在首页但把 `confirm()` 换成自制弹窗，做成「按住 3 秒发送」而不是一点就发。「强制刷新」这个功能本身建议直接从孩子界面删掉，需要时家长用 Safari 的清除网站数据。

**验证环节的补充/纠正**

严重度从 P2 上调到 P1，但要拆开看，三个子问题不同级：

- forceRefresh = P1（真正的 P1，撑起整条发现）：一个常驻 tab + 一次 confirm 就能不可逆地把离线能力删光。这个 App 的硬约束里明确写了「必须离线可用」，而这个按钮正好在最需要离线的场景（车上/飞机上）把离线打掉，且没网时无法自愈。破坏性 + 不可逆 + 无门槛，够 P1。
- 家长设置复选框 = P2：一点即生效地静默关掉通知，家长事后无感知，但可恢复。
- SOS = P2：误触只是给爸妈发一条假警报，尴尬但无损坏，且有 config.enabled 守卫兜底。

对建议修法的纠正：

1. 「forceRefresh 直接从孩子界面删掉，需要时家长用 Safari 的清除网站数据」这条不可行。iOS 上「添加到主屏幕」的 PWA 有独立的存储容器，Safari 里清除网站数据清不到 standalone PWA 的 SW 和 Cache Storage。而且 docs/踩坑记录.md 第 22 条明确写了维护者自己的调试流程就依赖 `getRegistrations()` 逐个 `unregister()` + `caches.delete()`（原文：「服务器发 Cache-Control: no-store 也拦不住，必须 getRegistrations() 逐个 unregister() + caches.delete()」）。删掉这个功能等于砍掉家长自己的调试手段。正确做法是保留函数、把入口挪到闸门后面。

2. 「问一道两位数加法 38+45」这个闸门在本项目里偏弱。数学游戏本身就在教加减法（mathConfig 支持到 30 的范围），一个练过的 7 岁孩子有可能用手指/纸算出来。建议换成明显超纲的形式：三位数乘法（如 `13×24`）或者「按住 3 秒」。

3. 「按住 3 秒」在 iOS Safari 上有个必踩的坑：`<button>` 上长按会触发系统 callout/选择菜单，打断手势。实现时必须在触发元素上加 `-webkit-touch-callout: none; -webkit-user-select: none; user-select: none;`，并在 touchstart 里 preventDefault。

4. SOS 改成「按住 3 秒发送」方向对，但注意别把真实紧急场景变难 —— 孩子慌张时长按比双重确认其实更容易完成，可接受；但不要再叠加第二道确认。

5. 顺带：如果做闸门，index.html:1646-1663 那三个 `onchange="updateNotifySetting(...)"` 复选框应该一起挪进去，它们比 Bark 输入框更容易被误触（输入框至少还要点「测试」才写入）。

6. 另有一个独立小问题可以顺手修：`confirm('确定要强制刷新吗？…')`（app.js:2108）和 `confirm('确定要发送紧急求助吗？')`（parentNotify.js:373）都是硬编码中文，而按钮标签走 i18n（en.js:118 `'profile.refresh': 'Force Refresh'`），非中文 locale 下弹窗对家长也不可读。

## 15. 画线砸怪兽/弹弹机器人转屏后画布被压扁，手指落点和线条位置错开约 40%

- **位置**：`js/drawSmash.js`:254
- **分类**：orientation-canvas

**孩子/家长会遇到什么**

孩子在 iPad 上横躺着玩，转一下屏：整个关卡画面被纵向压扁成矮胖的，画布下半部分（怪兽和地面所在的位置）看不见了；更糟的是在「Draw here」框里画一条线，线会画到比手指高出一大截的地方（纵向偏差约 40%），孩子会觉得「笔不听话」。唯一的恢复办法是退出关卡重新进入——但关卡进度会重来。弹弹机器人 ragdollRobot.js:395 完全一样。

**建议修法**

两个文件都在 startLevel 时挂上 resize 监听，退出关卡时移除：
```js
this._onResize = () => { 
  this._initCanvasSize();   // 内部会重算 canvasScale + 重设 canvas.width/height
  this._renderLevel();      // ragdoll 里不需要，游戏循环会自己重绘
};
window.addEventListener('resize', this._onResize);
```
注意 `_initCanvasSize()` 里每次都重新 `onpointerdown=...` 是幂等赋值，重复调用安全；但 `ctx.scale(dpr,dpr)` 依赖 `canvas.width=` 赋值把 transform 复位，顺序不能动。另外 iOS 上 resize 事件可能早于布局稳定，建议包一层 `requestAnimationFrame` 再测量。

**验证环节的补充/纠正**

建议的修法方向正确，但直接照抄会引入新问题，需要补三点：

1. **必须加零尺寸守卫**。结算界面 `_showScreen('draw-smash-result')` 会把 `#draw-smash-game` 整个 hidden 掉，此时 wrapper 的 `getBoundingClientRect()` 是 0x0 → `canvasScale = 0` → `canvas.width = 0`，后续 `_toLogical` 会除以 0 得到 Infinity。所以 `_initCanvasSize()` 开头应该加：
```js
if (containerW <= 0 || containerH <= 0) return;
```

2. **别用「startLevel 挂 / 退出时摘」的加减模式**，退出路径有 4 条（`closeModal` / `backToLevels` / `backToChapters` / 结算界面），漏摘一条就是泄漏 + 对隐藏元素乱测量。更省事的做法是模块 init 时挂一次，handler 里自己判断游戏屏是否可见：
```js
window.addEventListener('resize', () => {
    const el = document.getElementById('draw-smash-game');
    if (!el || el.classList.contains('hidden') || !this.canvas) return;
    requestAnimationFrame(() => this._initCanvasSize());
});
```

3. **ragdollRobot 的 handler 只能调 `_initCanvasSize()`，绝不能调 `_setupCanvas()`**。因为 `_setupCanvas` 的 rAF 里还有 `_startGameLoop()`（ragdollRobot.js:396-397），重复调会叠加游戏循环，物理速度翻倍。

其余几点原报告说得对：`onpointerdown = ...` 是幂等赋值，重复调安全；`canvas.width =` 赋值会复位 transform，所以 `ctx.scale(dpr,dpr)` 必须留在赋值之后，顺序不能动；iOS 上包一层 rAF 再测量也确实必要。drawSmash 的 `_initCanvasSize()` 结尾自带 `_renderLevel()`（drawSmash.js:290），模拟中途重调也安全，不需要额外补渲染。

另外可以顺手治根因：`#ds-canvas`/`#rr-canvas` 之所以会被压扁而不是等比缩，是因为内联同时写死了 style.width 和 style.height，`max-height:100%` 只夹一边。加上 `aspect-ratio: 2 / 3`（400:600）能让 CSS 侧退化时至少保持比例不变形，但**这只治画面变形，治不了触摸错位**——canvasScale 仍然是陈旧的，resize 监听还是得加。

## 16. 每次打开「画画创作」都重新绑一遍事件，监听器叠加 —— 第 N 次打开后一笔画会被画 N 遍

- **位置**：`js/drawing.js`:158
- **分类**：correctness

**孩子/家长会遇到什么**

孩子当天第一次画画一切正常。退出去玩别的、再回来画（很常见），同一根手指划过屏幕时 draw() 会跑 2 遍——同一段路径被叠画两次，半透明的蜡笔/马克笔（opacity 0.6~0.7）颜色明显变深变糊，霓虹/彩虹笔的效果也会变形。开到第五次以后每次 pointermove 跑 5 遍绘制逻辑，iPad 上画长线会明显掉帧卡顿。同时 window resize 监听也累积了 5 个，每转一次屏就跑 5 次 getImageData/putImageData（大画布上很贵）。孩子的体感是「画画越用越卡、颜色越来越怪」，重启 App 才恢复。

**建议修法**

给 init() 加幂等保护：把 bindEvents() 拆出去只在第一次执行（`if (!this._bound) { this.bindEvents(); this._bound = true; }`），resizeCanvas / clear / saveState 仍可每次执行。同理检查 openDrawing 之外的其他 init 调用点。

**验证环节的补充/纠正**

建议的修法可行，我核实过不会引入新问题：

1. `if (!this._bound) { this.bindEvents(); this._bound = true; }` 是安全的，因为 #drawing-canvas 是 index.html:1758 的静态节点，drawing.js 从不重建它（11 次 init 后节点身份不变，已实测）。绑一次即可长期有效。事件处理器内部走的是 `this.canvas` / `this.settings`，每次 init 重新赋值 this.canvas 指向同一节点，不受影响。

2. init() 里其余步骤（resizeCanvas / renderToolbar / renderTemplatePanel / renderStickerPanel / clear / saveState）继续每次执行没问题：drawing.js 全文件 addEventListener 只有 bindEvents 内的 7 处（197/206/207/208/211/212/215），那几个 render* 不加监听器，重复调用不会累积。

3. 更简单的等价写法：在 init() 开头 `if (this._inited) { this.resizeCanvas(); this.clear(); this.saveState(); return; }`，但拆 bindEvents 的写法更清楚，推荐原方案。

4. 关于"检查 openDrawing 之外的其他 init 调用点"：不用查了，我已经 grep 过，`DrawingApp.init()` 全仓库只有 drawing.js:1094 一处调用点，openDrawing 被 homeScreen.js:30 和 app.js:170 调用。

5. 顺带（可选，不必须）：drawing.js:215-220 的 resize handler 用 `getImageData(0,0,this.canvas.width,this.canvas.height)`（设备像素）配 `putImageData(imageData,0,0)`，横竖屏切换后画布尺寸变了，多出来的部分会丢/错位。这是独立于本条的另一个小问题，修幂等时顺手看一眼即可，不要混进本条。

6. 修完记得按 CLAUDE.md 的要求 bump sw.js 的 CACHE_NAME 版本号，否则 cache-first 的 SW 会让孩子的设备继续跑旧的 drawing.js（踩坑记录第 12 条）。

## 17. 保存画作时 localStorage 写满会抛未捕获异常，整个保存流程中断且没有任何提示

- **位置**：`js/drawing.js`:649
- **分类**：错误吞掉

**孩子/家长会遇到什么**

孩子画满十几二十幅画之后，再点「保存」——没有「画作已保存！」的提示、没有 +10 积分、爸妈也收不到「🎨 新画作完成！」的推送。孩子会以为按钮坏了，反复点，每次都一样。而且因为异常发生在写 gallery 这一步，从此再也存不进任何新画，旧画也不会被自动淘汰（slice(0,20) 那一步的结果根本没写进去）。

**建议修法**

给 saveToGallery 包 try/catch，catch 里做降级：先 `gallery = gallery.slice(0, 8)` 再重试一次 setItem，仍失败就 `alert('作品集满了，先删几幅旧画吧~')`；并把 saveArtwork 里的 addPoints / ParentNotify / alert 移到 saveToGallery 之前，保证存不进作品集也不影响「画完了有奖励」这件事。另外建议把 dataURL 换成 image/jpeg 0.8（体积约为 PNG 的 1/4）。

**验证环节的补充/纠正**

建议的修法方向对，但有一处是错的，且漏了根因。

【建议里错误的部分】`alert('作品集满了，先删几幅旧画吧~')` 不可行。我在全项目 grep "artworkGallery"，只有 drawing.js:650（读）和 drawing.js:658（写）两处，加上 CLAUDE.md:182 的存储表格说明——**根本不存在任何作品集查看/删除 UI**（index.html 里唯一的 "gallery" 命中是 photo-input-gallery 文件选择框，无关）。也就是说这 5MB 数据是只写不读的死存储，孩子永远看不到。对一个 5-7 岁、很多还不识字的孩子弹"先删几幅旧画吧"，既没有可删的地方，也读不懂，只会变成一个吓人的死胡同弹窗。

【推荐的修法，按优先级】
1. 最省事且最对症：既然作品集没有任何读取方，直接**不要往 localStorage 存**。saveArtwork 里已经通过 link.click() 触发了 PNG 下载到相册/文件，这才是家长真正能看到画的途径。删掉 saveToGallery 调用即可，一行改动，同时释放全部 origin 配额，顺带解决成就/宠物/错题本被挤爆的问题。如果家长确实想要作品集，那是另一个需要配套做查看 UI 的独立需求。

2. 如果一定要保留作品集：
   - saveToGallery 必须包 try/catch，catch 里循环 `gallery.pop()` 重试 setItem（不是固定 slice(0,8) 就重试一次——单幅可能就有 500KB+，砍到 8 幅仍可能超），直到成功或 gallery 为空。
   - 把幅数上限从 20 降到 3-5 幅，因为实测 iOS 5MB 只放得下 6-7 幅。
   - dataURL 换成 `toDataURL('image/jpeg', 0.8)`：实测同一幅 80 笔涂鸦 PNG 395,730 → JPEG 见测量组约降到 1/3~1/4，这条建议有效，但注意 JPEG 无透明通道，而画布本来就是白底（drawing.js:551 fillRect 白底），所以没有副作用。
   - 静默降级，不要弹任何错误 alert 给孩子。

3. 无论选哪条，报告里"把 addPoints / ParentNotify / alert 移到 saveToGallery 之前"这个建议是对的、必须做——保证存储失败不影响"画完了有奖励"这件事。

【顺带发现，不属于本条但相关】drawing.js:575-588 saveState() 的撤销历史是 maxHistory=20 幅 toDataURL 存在内存数组 this.history 里（不占 localStorage，不影响本条结论），但按实测单幅 380KB 算，内存里会常驻约 7.6MB 的 dataURL 字符串，在 iPad Safari 上有触发页面重载的风险。属于独立问题，建议另开一条。

## 18. 画画创作/书写练习每次进入都重新绑一遍画布事件，监听器无限叠加，撤销功能被打爆

- **位置**：`js/drawing.js`:195
- **分类**：内存泄漏

**孩子/家长会遇到什么**

孩子第 6 次打开画画后贴一个贴纸：
- 听到 6 声重叠的「咔」（音量叠加、发闷）
- 后台跑 6 次全画布 toDataURL（1536×1024 的 PNG 编码，iPad 上每次几十到上百毫秒）→ 贴一个贴纸卡顿半秒
- **20 格撤销历史被一次点击吃掉 6 格**，孩子按「撤销」，画面纹丝不动，要连按 6 次才退回一步；贴 3 个贴纸整个历史就满了，再也撤不回最初的样子。

书写练习那边同理：来回切几次模式后，一笔下去要跑 5 次 drawLine，在低端 iPad 上明显掉帧、笔迹跟不上手指。

**建议修法**

两个文件同一种改法，二选一：
1. **最省事**：加一个绑定标记，只绑一次。
```js
bindEvents() {
  if (this._bound) return;
  this._bound = true;
  ...
}
```
（`init()` 里其他的 resizeCanvas/renderToolbar 该重跑还是重跑，只跳过绑定。）
2. 或者把事件绑定从 `init()` 里挪出来，在 DOMContentLoaded 时绑一次，`openDrawing()` 只负责 resize + 清空。

writing.js:444 同样加 `if (this.free._bound) return; this.free._bound = true;`。

**验证环节的补充/纠正**

建议的修法一（`if (this._bound) return; this._bound = true;`）**可行且安全**，我核对过不会引入新问题：

- `bindEvents()` 里的闭包捕获的是 `this`（DrawingApp 单例）而不是局部 canvas 变量，运行时才 deref `this.canvas` / `this.ctx`，而 `#drawing-canvas` 是 index.html 静态节点、永不重建，所以「只绑一次」不会出现绑到旧节点的悬挂问题。
- `init()` 里剩下的 `resizeCanvas() / renderToolbar() / renderTemplatePanel() / renderStickerPanel() / clear() / saveState()` 照常重跑没问题：`canvas.width = ...` 会重置 2D context 的 transform，所以 `ctx.scale(dpr, dpr)` 不会累积。
- writing.js 同理，`this.free` 是个普通对象（writing.js:69-80），加 `_bound` 字段安全。

修法二（挪到 DOMContentLoaded 绑一次）也可行（两个 canvas 都在静态 HTML 里，DOMContentLoaded 时已存在），但改动面更大、收益一样，**建议直接用修法一**。

补充两点原建议没覆盖、顺手一起改成本极低的：

1. **`window` 上的 resize 也要一起被 `_bound` 守卫住**（原建议其实已经包含，但值得显式确认），另外可以在 handler 开头加一句 `if (this.canvas.parentElement.getBoundingClientRect().width === 0) return;`，避免画画模块关闭时横竖屏切换把画布尺寸置 0。

2. **`_bound` 只解决叠加，不解决单次的重复触发风险**。更稳妥的是在 `placeSticker`（drawing.js:915）和 `handleFillClick`（drawing.js:905）里也加一层同帧去重，例如记录 `this._lastActionTs`，同一 pointerId / 50ms 内直接 return。这样即便将来别处又多绑了一次，也不会再吃撤销历史。

3. 顺带一提（**不属于本条发现、不要合并修**）：`init()` 里 `clear()` 会清空画布但 `this.history` **没有重置**（drawing.js:158-170，对比 writing.js:421-424 是有重置的）。结果是孩子重新打开画画、画布是空白的，但按一下「撤销」会突然冒出上一次的画。这是独立的一个小问题，triage 时可以单开一条。

## 19. 画画创作转屏时会永久切掉孩子画的下半部分

- **位置**：`js/drawing.js`:215
- **分类**：orientation-canvas

**孩子/家长会遇到什么**

孩子在 iPad 上画了半天，把平板转个方向（比如从竖着改成横着放桌上），画的下面三分之一当场消失且不可逆——转回竖屏也回不来（像素已经在那次 putImageData 里丢了）。孩子只能重画。

**建议修法**

改成先存 dataURL、resize 后按新尺寸整幅重绘（自动缩放）：
```js
window.addEventListener('resize', () => {
  if (!this.canvas || !this.canvas.width) return;   // 画画没打开时别跑
  const snap = this.canvas.toDataURL();
  const oldW = parseFloat(this.canvas.style.width);
  this.resizeCanvas();
  const img = new Image();
  img.onload = () => {
    const w = parseFloat(this.canvas.style.width);
    this.ctx.drawImage(img, 0, 0, w, w * (img.height / img.width));
  };
  img.src = snap;
});
```
另外这个监听是无条件绑在 window 上的，画画关掉后转屏也会跑，加上开头那句 guard 顺便修掉。

**验证环节的补充/纠正**

建议的修法方向对（先快照、resize 后整幅重绘），但**照抄会让情况更糟**，有三个必须改的点：

1）**按宽度等比缩放是错的，必须用 contain（取 min）**。原建议 `drawImage(img, 0, 0, w, w * (img.height/img.width))`：竖屏 366x411 → 横屏 804x169 时算出来是 804x903 CSS px，画进一个只有 169 高的画布，等于把画放大 2.2 倍后只剩顶部 18.7% 可见——比现在「保留顶部 41% 且比例正确」还差。正确写法（同时居中、留白）：
```js
const dpr = window.devicePixelRatio || 1;
const iw = img.width / dpr, ih = img.height / dpr;   // 旧画的 CSS 尺寸
const s = Math.min(w / iw, h / ih);                   // contain
this.ctx.drawImage(img, (w - iw*s)/2, (h - ih*s)/2, iw*s, ih*s);
```
（注意 img 是位图尺寸，必须先除 dpr 再和 CSS 尺寸比，否则又会撞上 restoreState 那个放大 dpr 倍的坑。）

2）**别用 Image + onload 这种异步恢复，iOS 转屏时 resize 会连续触发多次**。第二次 resize 的 toDataURL 会拍到「已经被 resizeCanvas 清空、但上一张 img 还没 onload」的空白画布，结果整幅画变全白——比现在的裁一半更惨。改成同步走离屏 canvas：
```js
const snap = document.createElement('canvas');
snap.width = this.canvas.width; snap.height = this.canvas.height;
snap.getContext('2d').drawImage(this.canvas, 0, 0);
this.resizeCanvas();
// 然后同步 drawImage(snap, ...) 按上面的 contain 公式
```
同步做完，多次 resize 也不会打架。

3）**监听必须只绑一次**。openDrawing → init → bindEvents 每次都重复绑（实测「打开-退出-再打开」后一次 resize 跑 2 次 resizeCanvas）。如果保留异步版恢复，多个监听会互相覆盖快照直接把画搞没；就算改成同步版，也是白白多做几遍 toDataURL。在 bindEvents 开头加 `if (this._bound) return; this._bound = true;`，或者把 resize 监听单独提到 init 外面绑一次。

4）guard 建议改成判模态框可见性而不是判 `canvas.width`：画画关掉后第一次转屏时 canvas.width 还是上一次的非零值，原 guard 拦不住，画布照样被设成 0x0。用
```js
const modal = document.getElementById('drawing-modal');
if (!this.canvas || !modal || modal.classList.contains('hidden')) return;
```
既挡住了 0x0，也顺手消掉那两条 IndexSizeError。

5）另有一条独立 bug 建议单开工单：restoreState()（drawing.js:607-613）和 toggleDarkMode()（561-570）都用 `drawImage(img, 0, 0)` 把位图尺寸的快照画进带 scale(dpr,dpr) 的 ctx，导致**每按一次撤销/重做/切黑底，画就被放大 dpr 倍（iPhone/iPad 上 = 2 或 3 倍）**。实测 (10,10,50,50) 的方块 undo 后变成两倍大且位置翻倍。这条按 P1 报，因为「撤销把画搞坏」比转屏更高频。

补充：还有个纯观感问题，转屏后画布变宽，contain 方案会在两侧留白边（画只占中间一条）。对 5-7 岁孩子来说「画还在、只是变小了」远好过「画没了」，可以接受；如果想更好看，可以在留白处填当前底色（darkMode ? '#1a1a2e' : '#FFFFFF'），别留透明。

## 20. 全项目 0 处 QuotaExceededError 处理；artworkGallery 存 20 张全分辨率 PNG base64 且没有任何界面能看到它们

- **位置**：`js/drawing.js`:649
- **分类**：配额/异常处理

**孩子/家长会遇到什么**

孩子画完点保存：按钮按下去，没有「画作已保存！」提示，没有 +10 分的星星特效，爸妈手机上也收不到推送——看起来就是「点了没反应」，他会一直反复点。等配额被 20 张画撑满以后，去做数学题：答对了按钮变绿，然后就停在那儿，下一题永远不出来，整个数学游戏卡死。而这 20 张吃掉全部配额的画，应用里根本没有任何入口能看到。

**建议修法**

三步：
1. saveToGallery 立刻改成有损压缩 + 限尺寸 + 按字节封顶：`canvas.toDataURL('image/jpeg', 0.7)`，先 drawImage 到 max 800px 的离屏 canvas，张数降到 6，并在写入前累计 `JSON.stringify(gallery).length > 1.5e6` 就从尾部丢弃。
2. 给 setItem 加统一封装，配额满时降级而不是抛：
```js
function safeSet(key, val) {
  try { localStorage.setItem(key, val); return true; }
  catch (e) {
    if (e && (e.name === 'QuotaExceededError' || e.code === 22)) {
      localStorage.removeItem('artworkGallery');       // 先丢可再生的大件
      localStorage.removeItem('videoWhitelistCache');
      try { localStorage.setItem(key, val); return true; } catch (_) {}
    }
    return false;                                       // 绝不往上抛
  }
}
```
把所有模块的 saveData/saveStats 改走 safeSet。
3. 要么补一个作品集查看界面，要么直接删掉 saveToGallery（saveArtwork 已经触发了下载，孩子的画在相册里）。

**验证环节的补充/纠正**

建议的三步方向对，但有三处要改，否则会引入新问题：

## 26. 紧急求助（SOS）无论发送成功还是失败，都告诉孩子「已发送，爸爸妈妈会很快来的」

- **位置**：`js/parentNotify.js`:365
- **分类**：child-safety

**孩子/家长会遇到什么**

孩子真的害怕/受伤时按下 🆘：手机没信号、在飞行模式、连着没网的 WiFi、家长的 Bark URL 填错或过期——任意一种情况下，孩子看到的都是「已发送紧急求助！爸爸妈妈会很快来的~」，然后坐在那里等一个永远不会来的人。而且 fetch 没超时，弹窗要等几十秒才出现，孩子这段时间完全没反馈，会以为按坏了而反复按。

**建议修法**

1) 检查返回值并如实告知：
```js
const ok = await ParentNotify.notifySOS();
alert(ok ? '已发送！爸爸妈妈马上就知道了~'
         : '❌ 没发出去！快去找身边的大人，或者按下面的电话按钮');
```
2) 给 sendToOne 加超时 + 重试（SOS 走 3 次）：
```js
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 6000);
const response = await fetch(url, { signal: controller.signal });
```
3) 失败时给一个不依赖数据网络的兜底：家长设置里加一个「紧急电话」字段，失败后渲染大按钮 `<a href="tel:138xxxx">📞 打给妈妈</a>`——蜂窝通话在没数据网络时依然可用。
4) 发送期间显示「正在通知爸爸妈妈…」的全屏状态。

**验证环节的补充/纠正**

建议的 4 条修法整体可行，但有几个会引入新问题的坑，按可做性排序：

1) 【立刻可做，零风险】检查返回值。这是本条的核心，改 :381-384 两行即可，无副作用。

2) 【sendToOne 的成功判据要放宽，否则修完会产生新的谎报——方向相反的那种】现在 :74-75 是 `const result = await response.json(); return result.code === 200;`。自建 bark-server / 反代返回纯文本或 204 时，推送其实已经发出去了，json() 抛异常 → 返回 false → 修完之后会告诉孩子「❌ 没发出去」，把成功说成失败。在紧急场景这同样有害。建议：
```js
const response = await fetch(url, { signal });
if (!response.ok) return false;              // HTTP 层面失败才算失败
try { const r = await response.json(); return r.code === undefined || r.code === 200; }
catch { return true; }                        // 2xx 但不是 JSON，按成功处理
```
注意 api.day.app 对无效 key 返回的是 HTTP 400（我实测 /ping 走的是标准 JSON + code 字段），所以 response.ok 这道判据对官方服务依然能正确识别过期 key。

3) 【超时+重试要连带算总时长，否则体验反而更差】AbortController + fetch signal 在 iOS Safari 12.1+ 支持，可用。但注意 send() 里 :89-92 是 Promise.all 并行发爸爸和妈妈，所以 3 次重试的最坏时长是 6s×3 ≈ 18s（不是 36s）。18 秒的空白等待比现在「立刻弹一个假成功」更折磨人 —— 所以第 4 条（发送期间的全屏「正在通知爸爸妈妈…」状态）不是锦上添花，是第 2、3 条的前置条件，必须一起做，否则别单独加重试。另外重试期间孩子可以重复点 🆘 图标（await 期间 UI 是响应的，只是会再弹一次 confirm），最好在发送中禁用该入口。

4) 【tel: 兜底在 iPad 上会落空】孩子主力设备是 iPhone/iPad，iPad 无蜂窝、没配 FaceTime 时点 `<a href="tel:">` 要么无反应要么弹 FaceTime 授权框，等于没兜底。建议同时给 `facetime://` 备选，并且无论如何都把号码用超大字号直接显示在屏幕上（孩子可以拿去给旁边的大人看）。号码存 localStorage 明文，与现有 Bark URL 同等风险，纯静态站点下可接受。

5) 【比换 alert 文案更根本的一点】:372 的 confirm() 和 :367/:384 的 alert() 全是中文文字，对目标年龄段（不识字/刚识字）等于不可用，而且 alert/confirm 在 iOS PWA 里样式无法控制。真正的修法应该是图形化：大红叉/大绿勾 + 复用项目已有的 js/puterTTS.js 把结果念出来（「没有发出去，快去找旁边的大人」）。这样成功/失败对不识字的孩子才真正可分辨。这一步比单纯改文案更值，但工作量也更大，可以分两次做：先做第 1 条止血，再做图形化+语音。

6) 顺带（不属于本条，triage 时可合并考虑）：triggerSOS 里的提示语是硬编码中文，没走 I18n.t，而应用支持 7 种语言。

## 27. 家长设置零门槛，孩子可以自己把 Bark URL 删掉，从而静默关掉 SOS 和全部家长通知

- **位置**：`js/parentNotify.js`:242
- **分类**：child-safety

**孩子/家长会遇到什么**

孩子随手点开「家长设置」，把输入框里那串看不懂的字删掉再点「测试」→ 家长从此收不到任何通知，而且**没有任何人会被告知**。等到孩子真的需要按 🆘 时，得到的是「还没有设置家长通知，请先让爸爸妈妈设置~」。更隐蔽的版本：孩子改错 URL 一个字符，测试显示失败，但坏值已经被写进 localStorage 持久化了。

**建议修法**

1) 加一个「改一个配置就生效」的家长门（不需后端）：
```js
function parentGate() {
  const a = 7 + Math.floor(Math.random()*6), b = 6 + Math.floor(Math.random()*7);
  return prompt(`家长验证：${a} × ${b} = ?`) === String(a*b);
}
// openParentSettings() 开头： if (!parentGate()) return;
```
5-7 岁做不出两位数乘法，家长两秒就过。
2) 把 `ParentNotify.setBarkUrl(who, url)`（js/parentNotify.js:264）挪到 testNotify 成功之后，失败就不落盘。
3) Bark URL 输入框平时只显示后 4 位（或 type=password）。

**验证环节的补充/纠正**

维持 P1（不升 P0：今天功能没坏，需要孩子主动操作才触发；不降 P2：一旦触发是静默的，且打掉的是紧急求助通道，家长零感知）。

对建议修法的纠正：

1) **建议 2 按字面写会引入新 bug，必须改**。`testNotify(who)` 是从 config 里读 URL 的（js/parentNotify.js:173-175：`const url = who === 'dad' ? this.config.dadBarkUrl : this.config.momBarkUrl;`）。如果把 :264 的 `setBarkUrl` 挪到 testNotify 之后，testNotify 测的是**旧值**（首次配置时是空串，`sendToOne` 第一行 `if (!barkUrl) return false` 直接返回 false，永远配不上）。正确做法是让 testNotify 接受显式 URL，或在 saveBarkUrl 里先按 setBarkUrl 的规则补尾斜杠、直接调 `ParentNotify.sendToOne(normalizedUrl, ...)`，成功后再落盘。
   另外「失败就不落盘」有副作用：离线/Bark 服务抖动时，家长输入的正确 URL 也会存不进去。建议失败时提示「没存下来，请联网后重试」，而不是静默丢弃。

2) **家长门是可行的**：prompt() 在本项目已被使用（js/choreTracker.js:798），iOS Safari 和 standalone PWA 都支持。因为只有 homeScreen.js:65 和 app.js:178 两个入口、且都走 `openParentSettings()`，在函数开头加一行守卫即可全覆盖，符合「改一处就生效」。两点注意：prompt 文案要走 I18n（应用支持 7 种语言，硬编码中文会让其他语言下的家长看不懂）；乘法题建议避开 ×10 这类整十数，别选出 7×10 这种大孩子能口算的。

3) **门必须同时挡住弹窗里的复选框**，这正是加在 openParentSettings() 开头的好处——URL 输入框和 3 个即时生效的通知开关一起被挡在门后。

4) 建议 3（type=password / 只显示后 4 位）优先级最低，加了门之后收益很小；`type="password"` 在 iOS 上还可能触发钥匙串自动填充弹窗，干扰家长粘贴 Bark URL。可以不做，或退而求其次做成「聚焦时才显示全文」。

5) 建议顺带修 triggerSOS（js/parentNotify.js:381-384）：拿 notifySOS() 的返回值分支提示，失败时明确告诉孩子「没发出去，快去找大人」，而不是无条件 alert「已发送」。这条独立于家长门，成本极低，且是这个故事里对孩子伤害最直接的一环。

6) choreTracker 的「重置积分/清空记录」（js/choreTracker.js:828/840）不在这个门后面，如果要一并解决需要单独处理——但那属于另一条发现，不要混进这条的修复范围。

## 28. 魔法公园每进一次就多一个 canvas 点击监听 + 一个永不关闭的 AudioContext

- **位置**：`js/parkWallpaper.js`:208
- **分类**：内存泄漏

**孩子/家长会遇到什么**

onTap 的兜底分支是 `this.spawnSparkles(x, y, 8); this.playMagicChime();`。孩子第 4 次进公园后点一下天空：一次性冒出 32 个亮片、4 声魔法音同时响（音量叠成一坨、破音）；点太阳/云朵/喷泉同样触发 4 次特效，画面变得又吵又乱，和第一次进来的体验完全不一样。玩十几次后每点一次屏幕要算 80+ 个粒子，低端 iPad 会掉帧。

同时 4 个（玩 10 次就 10 个）running 状态的 AudioContext 一直挂着，每个占一条音频线程；iOS 上 AudioContext 数量有硬上限，超了 `initSoundEngine()` 的 try/catch 会静默吞掉异常，之后新一轮的音效引擎就建不起来了。

**建议修法**

在 `stopScene()` 里补两处（和 birthdayParty 保持一致）：
```js
stopScene() {
  ...
  if (this._tapHandler) {
    this.canvas.removeEventListener('pointerdown', this._tapHandler);
    this._tapHandler = null;
  }
  if (this.soundCtx) {
    try { this.soundCtx.close(); } catch (e) {}
    this.soundCtx = null;
  }
  ...
}
```
对应 `startScene()` 里改成具名引用：
```js
this._tapHandler = (e) => this.onTap(e);
this.canvas.addEventListener('pointerdown', this._tapHandler);
```

**验证环节的补充/纠正**

建议的修法可行，我核查过不会引入新问题，只补三点：

1. **soundCtx 置 null 是安全的**——所有发声函数开头都有守卫，我逐个确认过：playTone:405、playWindSound:421、playBirdChirp:443、playSplash:451、playBikeBell:475、playMagicChime:482、playRainSound:490 全是 `if (!this.soundCtx) return;`。playBirdChirp/playMagicChime 用 setTimeout 延迟发声，close 后这些回调会走进 playTone 的守卫直接 return，不会抛错。

2. **stopScene 里加 `this.canvas &&` 保险**。目前 closeParkWallpaper()（4404 行）走的是 ParkWallpaper.close()，不调 stopScene，所以没有"未 start 先 stop"的路径；但 stopScene 是挂在 onclick 上的公开入口，加个判空成本为零：
```js
if (this._tapHandler && this.canvas) {
  this.canvas.removeEventListener('pointerdown', this._tapHandler);
  this._tapHandler = null;
}
```

3. **不要改成"只绑一次"的方案**。因为 #pw-fs-canvas 是常驻节点，有人会想用 `if (!this._tapBound) { ...; this._tapBound = true; }` 一次性绑定、soundCtx 也常驻复用。不建议：iOS 上应用切后台再回来，复用的 AudioContext 会变成 suspended，之后所有音效静音，还得额外写 resume() 逻辑。原建议的"每次 start 新建 / 每次 stop close"更稳（startScene 由 onclick 触发，处于用户手势内，新建的 context 直接是 running，我实测 soundCtxState 就是 running），而且和 birthdayParty.js 的写法保持一致。

4. 顺带确认**这个模块没有别的同类泄漏**：initVoiceRecognition（2354）配套的 stopVoiceRecognition（2411）有 stop+abort+置 null，麦克风 audioCtx（311/330）有 close，rAF 有 cancel。只有 pointerdown 和 soundCtx 两处漏了，改这两处就干净了。

## 32. 每次音效都 new 一个 AudioContext 且从不 close，iOS 上会导致音效永久消失

- **位置**：`js/rewards.js`:284
- **分类**：资源泄漏

**孩子/家长会遇到什么**

WebKit 对单个页面能同时存在的 AudioContext 有硬上限（历史上是 4 个），超过后 `new AudioContext()` 直接抛异常 —— 而这里的 catch 是空的，所以**不会报错，只会安静地不出声**。孩子做完前几道题之后，答对不再有「叮」的上升音、点击没有反馈音、通关没有庆祝音，而奖励音效正是这个年龄段唯一的即时正反馈；家长会以为「iPad 静音了」。

```js
  if (this._ctx.state === 'suspended') this._ctx.resume();
  return this._ctx;
},
playSound(type) {
  try {
    const audioContext = this._audioCtx();
    ... // 下面原封不动
```
顺便把空 catch 改成 `catch (e) { console.warn('playSound', e); }`，下次再出这种问题至少 console 里看得见。

**验证环节的补充/纠正**

建议的单例修法方向正确（和 music.js 一致），但直接照抄会引入一个新风险，必须补两点：

1) `state === 'suspended'` 判断不够。iOS WebKit 有非标准的 `'interrupted'` 状态（来电、切后台、PWA 被系统挂起后回来）。单例一旦卡在 interrupted 而代码只在 suspended 时 resume，全站音效就会**真的永久消失**——反而把今天「每次新建所以能自愈」的行为变成了不可恢复的故障。改成：
```js
_ctx: null,
_audioCtx() {
  if (!this._ctx || this._ctx.state === 'closed') {
    this._ctx = new (window.AudioContext || window.webkitAudioContext)();
  }
  if (this._ctx.state !== 'running') this._ctx.resume().catch(() => {});
  return this._ctx;
}
```
（`state !== 'running'` 同时覆盖 suspended / interrupted；closed 时重建兜底。）

2) 单例下节点会累积一点垃圾，加一行更稳妥：`oscillator.onended = () => { try { gainNode.disconnect(); } catch (e) {} };`。振荡器 stop 后自身会被释放，但显式断开 gainNode 更保险。

3) 空 catch 改 `console.warn('[RewardSystem] playSound 失败:', e)` 这条同意，且是本条里最该做的——没有它下次同类问题依然是零线索。

4) 同一个 bug 的第二处：js/writing.js:706-709 也是每次 new AudioContext 且不 close，建议同批修（或直接改成调 RewardSystem.playSound）。js/choreTracker.js:882、js/parkWallpaper.js:311/400、js/birthdayParty.js:977 已经有 close，不用动。

5) 落地提醒：改完记得 bump sw.js 版本号，否则 cache-first 的 SW 会让改动到不了 iPad 上（踩坑记录第 12 条）。

6) 由于当前工作区 js/rewards.js 已被另一笔未提交的改动占用（loadData 的 try/catch 加固），改这里要注意别覆盖那笔改动——两处不冲突，但同文件并发编辑容易互相丢。

## 33. 6 个模块的 loadData 直接用 JSON.parse 结果整体替换默认对象，没有版本号也没有迁移机制，加一个字段就让老用户看到 NaN

下次给 RewardSystem 或任意 stats 加一个新计数字段，所有老用户（数据里没这个字段）第一次触发就得到 `undefined++` = NaN，之后 NaN 会一路传染：首页总积分显示 NaN，成就页进度显示「NaN/10」，而 `NaN >= target` 恒为 false，那一整类成就再也解锁不了——且因为 NaN 已经落盘，卸载重装都修不好。孩子看到的就是自己的分数变成三个奇怪的字母。

```js

  let d = {...defaults, ...(safeParse(key) || {})};
  if (migrate && d._v !== defaults._v) { d = migrate(d, d._v); d._v = defaults._v; }
  return d;
}
```

**验证环节的补充/纠正**

建议的修法方向正确（同源优先 + CDN 兜底 + 进 precache + 库本地化），但落地时有 4 个坑必须一起处理，否则会引入新问题：

1) precache 的一次性失败风险（踩坑记录 #14）：`cache.addAll()` 只要一个 URL 404 整个 SW 安装失败。40 个 `/data/hanzi/*.json` 一次性塞进 urlsToCache 会把「少抓了一个字」放大成「整个 App 离线全废」。更稳的做法是把汉字数据单独用一次 `cache.open().then(c => Promise.allSettled(hanziFiles.map(f => c.add(f))))`，或者至少在生成脚本里断言 40 个文件都存在再提交。同时别忘了踩坑 #12：必须 bump CACHE_NAME。

2) 光修数据不修库等于没修：hanzi-writer.min.js（实测 36,462 字节）同样在 CDN 上。首次离线/CDN 被墙时库根本加载不到，走的是 writing.js:205 的 `<p style="color: red;">Hanzi Writer 加载失败</p>` —— 对不识字的孩子是一片空白加一行红字。必须把库下到 js/vendor/ 走同源并进 precache，这一步优先级不低于数据本地化。

3) 授权问题（原建议没提）：hanzi-writer-data 的 npm license 字段是 `SEE LICENSE IN ARPHICPL.TXT`（源自 Make Me a Hanzi，Arphic Public License），不是 MIT。抓进仓库是允许的，但要把 ARPHICPL.TXT / 出处说明一并放进 data/hanzi/ 或 README，避免裸拷贝。

4) 文案：改成儿童/家长看得懂的「这个字暂时加载不出来，连上网再试试~」是对的，但既然 fetch 有了同源兜底，真 404 的情况（未来往 characters 里加生僻字）依然存在，建议区分 `res.status === 404` → 「这个字还没收录」与网络失败 → 「连上网再试试」。另外这个模块 UI 用 data-i18n，而 showToast 现有调用（writing.js:220/390/677）全是硬编码中文，保持硬编码与现状一致即可，不必为这一条单独引 i18n。

补充一个原建议漏掉的边界：charDataLoader 的 catch 里从不调用 onComplete，HanziWriter 会永远停在「等数据」状态，随后 writing.js:196 的 `setTimeout(..., 500)` 里 `this.chinese.writer._character` 为空，笔画数停在 0/0，循环动画也不会启动 —— 所以失败时不只是空白，「播放笔顺 / 开始练习」三个按钮点了也毫无反应（实测点击 startCharacterQuiz() 无任何报错也无任何反馈）。修的时候建议在失败分支里同时给个可见的「重试」入口，而不是只靠 2 秒就消失的 toast。

## 36. 书写练习（汉字笔顺）离线完全不可用，且报错文案是误导性的「暂不支持此汉字」

- **位置**：`js/writing.js`:180
- **分类**：pwa-offline

**孩子/家长会遇到什么**

你的硬约束里写了「核心功能必须离线可用」，但书写练习是离线全废的：车上/飞机上/信号差的时候孩子点开书写练习，要么看到一行红色的「Hanzi Writer 加载失败」（不识字的孩子只知道「坏了」），要么田字格出来了、点哪个字都弹「暂不支持此汉字」——这句话是**假的**，字是支持的，只是没网。孩子会以为是自己选错了字，换一个还是同样提示。

**建议修法**

两步：
1. 把 hanzi-writer 的 JS 下载到 `js/vendor/hanzi-writer.min.js`，改成同源加载并加进 sw.js 的 `urlsToCache`（记得 bump CACHE_NAME）。
2. 笔画数据按需缓存——在 sw.js 的 fetch 里为这个域名开个例外，用 stale-while-revalidate：
```js
if (url.hostname === 'cdn.jsdelivr.net' && url.pathname.includes('hanzi-writer-data')) {
  event.respondWith(caches.open(CACHE_NAME).then(c =>
    c.match(event.request).then(hit => hit ||
      fetch(event.request).then(r => { c.put(event.request, r.clone()); return r; }))));
  return;
}
```
这样孩子练过的字下次离线也能练。同时把 catch 里的文案按 `navigator.onLine` 区分：离线时说「先连上网才能学这个字哦」，别再说「暂不支持」。

**验证环节的补充/纠正**

建议的第 1 步（vendoring hanzi-writer.min.js 到 js/vendor/ + 加进 urlsToCache + bump CACHE_NAME）可行且正确，文件只有约 36KB（实测 content-length 0x8e6e = 36462 字节）。注意踩坑记录第 14 条：必须先把文件提交进仓库再往 urlsToCache 里加，否则 `cache.addAll()` 一个 404 会让整个 SW 安装失败，全站离线全废。

第 2 步（给 cdn.jsdelivr.net 在 sw.js 里开跨域例外做 stale-while-revalidate）技术上能跑通（jsDelivr 实测返回 `access-control-allow-origin: *`，writing.js 的 fetch 是 cors 模式，拿到的不是 opaque response，`cache.put` 不会抛），但**不建议这么修**，有更简单更彻底的做法：

- 汉字表是写死的 40 个字（js/writing.js:10-56），每个字的 json 实测 373~2476 字节，全部加起来大约 40~60KB。直接在 CI 或本地跑个一次性脚本把这 40 个 json 拉下来，合并成一个同源文件（比如 data/hanziStrokes.json 或 js/hanziData.js），charDataLoader 改成从本地对象取，然后加进 urlsToCache。这样：完全离线、零跨域、零 SW 特例、字表增删就是改一个数据文件——比 SW 例外更贴合「改一个配置文件就生效」，也符合踩坑记录第 5 条「需要跨域数据就在 CI 里预生成静态文件」的既定结论。SW 例外方案只能救「在线练过的字」，还会让缓存无限增长。
- ⚠️ 授权注意：hanzi-writer-data 的 package.json 写的是 `"license": "SEE LICENSE IN ARPHICPL.TXT"`（数据源自 Make Me a Hanzi，Arphic Public License）。打包进仓库属于再分发，需要把 ARPHICPL.TXT 一起放进仓库（比如 data/ARPHICPL.TXT）。hanzi-writer 库本身是 MIT，vendoring 时保留头部版权注释即可。

文案部分补充：
- 除了按 `navigator.onLine` 区分文案，还应处理「脚本本身没加载」那条路径（writing.js:205 的红字），两处都要给孩子看得懂的东西——建议统一成一个大表情 + 一句话（如「📶 先让爸爸妈妈连上网，就能学写字啦」），别用红色报错样式，别用「Hanzi Writer」这种英文技术词。两处文案都没走 i18n（硬编码中文），顺手补 i18n key。
- 还有一个原发现没提到的点：数据加载失败后「播放笔顺」按钮仍然可点且点了完全没反应（我实测 animateCharacter 不抛错也不做任何事），建议加载失败时把控制按钮 disable 掉，否则孩子会反复戳一个死按钮。
- 顺带：田字格伪元素写了 `border-style: dashed` 却用 background 画线（css/style.css:10700-10720），dashed 不生效，线是实线——不影响功能，只是和注释意图不符。

## 37. Service Worker 用 cache.put 存音乐的 206 响应必定抛异常，导致睡眠音乐永远缓存不上、离线放不出来

- **位置**：`sw.js`:112
- **分类**：离线/缓存

**孩子/家长会遇到什么**

1. **离线时孩子点睡眠音乐 → 直接失败**：缓存里从来没有音乐 → catch 分支拿到 undefined → `<audio>` 触发 error → 弹出 `alert('音乐加载失败，请检查网络连接')`。项目的硬约束写着「核心功能必须离线可用」，睡前哄睡音乐恰恰是最需要离线的场景（家里路由器关了、在车上、在飞机上）。
2. **在线时每晚重下**：圣诞轻音乐 55MB、超级放松音乐 54MB，每次播放都从头下载，走流量套餐一晚上就几十兆。
3. 每次播放还会在 SW 里产生一次未捕获的 Promise rejection。

**建议修法**

音乐不要在 fetch 拦截里顺手 put，改成「显式整文件预热」：
```js
// 1. 拦截逻辑只做兜底，别再 put，并且加 catch 防止未处理拒绝
if (isMusic(url)) {
  event.respondWith(
    caches.match(event.request, { ignoreSearch: true })
      .then(hit => hit || fetch(event.request))
  );
  return;
}

// 2. 由页面在孩子第一次点某首歌时发消息，SW 用不带 Range 的完整请求缓存它
self.addEventListener('message', e => {
  if (e.data?.type === 'CACHE_MUSIC') {
    e.waitUntil(caches.open(CACHE_NAME).then(c =>
      fetch(e.data.url, { cache: 'reload' })      // 无 Range → 200
        .then(r => r.ok && c.put(e.data.url, r))
        .catch(() => {})
    ));
  }
});
```
另外 55MB 的曲子对儿童 app 偏重，可以考虑用更低码率重压一遍（128kbps 单声道足够哄睡），55MB 能降到 10MB 以内。

**验证环节的补充/纠正**

建议修法方向正确，但有 3 处需要纠正/补充，直接照抄会踩坑：

【纠正 1：重压码率那段是错的，别做】原文说「55MB 用 128kbps 单声道重压能降到 10MB 以内」。实测 ffprobe：
```
christmas-light-music.mp3    bit_rate=64000  duration=7254s (2h)   55MB
super-relaxing-music.mp3     bit_rate=64000  duration=7116s        54MB
orchestral-lullabies.mp3     bit_rate=64000  duration=3750s        29MB
white-noise-sleep.mp3        bit_rate=64000  duration=2328s        18MB
dida-lullaby.mp3             bit_rate=192000 duration=88s          2.0MB
```
四个大文件**已经是 64kbps 立体声**，比建议的 128kbps 还低一半。体积大是因为时长 2 小时，不是码率高。转 128kbps 只会变大。真正的杠杆是**缩短时长**——`<audio>` 本来就带 `loop`（index.html:1591），5 分钟的循环片段听感完全一样，55MB 能降到 ~2.4MB，而且顺带把缓存配额问题一起解决了。反倒是 dida-lullaby.mp3 是唯一码率偏高（192kbps）的，但它才 2MB，无所谓。

【纠正 2：iOS 上 SW 能不能拦 media 请求，我没验证成，是这个修法最大的未知数】我的端到端复现跑在 Chrome 上，确认了 SW 能看到 `<audio>` 的 Range 请求。但 WebKit 长期存在「media element 的加载走 CoreMedia 独立通道、不经过 Service Worker」的行为，我没有 iOS 设备无法实测。如果 iOS 上确实绕过 SW，那么「预热完整文件到 Cache」在 iPad 上依然放不出离线音乐——缓存是满的，但 `<audio>` 根本不去问 SW。**这个必须在真机 iPad 上验一次再宣布修好**，否则会以为修了其实没修。
真机若确认 iOS 绕过 SW，唯一可靠路径是绕开 media 加载通道：页面里 `fetch(url)` → `blob` → 存 IndexedDB（不要放内存，55MB blob 在 iOS 上很容易被杀页面）→ 播放时 `audio.src = URL.createObjectURL(blob)`。

【纠正 3：别在「孩子第一次点某首歌」时自动预热】原文建议第一次点播就发 CACHE_MUSIC。孩子睡前随手点一下「圣诞轻音乐」，就会在后台静默拉 55MB 完整文件——如果在车上用蜂窝网，这比现在的 bug 更糟。而且 5 个文件合计 156MB 全塞 Cache API 有配额风险（iOS 尤其）。建议改成家长可见的显式开关：音乐卡片上加一个「⬇️ 存到本地」按钮（家长点），或者放进家长设置里。配合纠正 1 把文件缩到几 MB，自动预热才安全。

【补充：立即可做的 2 行止血（与离线方案无关，先做）】
sw.js:117 改成 `if (response.ok && response.status !== 206)`，并给 put 加 `.catch(() => {})`。这不解决离线，但能消掉每次播放一次的未捕获 Promise rejection，也让日志干净、以后排查不被干扰。

【补充：一个会放大伤害的相邻问题（顺手一起改）】js/app.js:2218 的 error 监听器是在 `initSleepMusic()` 里注册的，而 `initSleepMusic()` 被调用了两处且都可重复触发：js/app.js:2640（DOMContentLoaded）+ js/app.js:299（**每次**进入 sleep-music 页面都调一次）。监听器不断累加，从不移除。后果：孩子离线时第 3 次打开睡眠音乐页再点歌，会连续弹出 **3 个** `alert('音乐加载失败，请检查网络连接')`，每个都要点确定才能关。对 5-7 岁不识字的孩子来说，连弹的英文式模态框等于把 app 卡死。顺带说，这个 alert 文案本身也不该给孩子看——应该换成页面内的图形提示（比如卡片变灰 + 😴 图标），文字提示留给家长端。

【一个已验证可用的细节，可以放心】我实测确认：先用不带 Range 的请求 `cache.put` 存入 200 完整响应后，后续**带 Range 的请求 `caches.match` 能命中**（返回 HIT 200）。也就是说建议里「拦截逻辑只 `caches.match(event.request)` 兜底」这一步在 Chrome 上是成立的，不需要额外做 Range 切片处理。

## 39. 首页第 4 屏「工具」tab 被屏幕右边裁掉，滑到第 4 屏时也没有任何 tab 高亮

```js
const el = document.querySelectorAll('.home-tab')[i];
if (el) el.scrollIntoView({ block: 'nearest', inline: 'center' });
```
（注意踩坑记录第 11 条：这个容器没有 scroll-snap，scrollIntoView 是安全的。）

**验证环节的补充/纠正**

两个建议都需要修正后才能用。

【修法 (1) 平分宽度：方向对，但原样贴上去会在英/德/西/法下把文字挤出胶囊外】
实测把 `overflow-x:visible` + `.home-tab{flex:1 1 0;min-width:0;padding:10px 6px;justify-content:center}`
应用后，四个胶囊变成 [20,96][106,183][193,269][279,355]——中文下完美，零裁切零溢出。
但 `.home-tab` 有 `white-space: nowrap`（css/style.css:352）且**没有 overflow:hidden**，
所以拉丁语种的文字会直接画到白色圆角胶囊外面：
- 英文（默认语言）「Favorites」label right=104，胶囊 right=96 → 溢出 8px
- 德文「Werkzeuge」label right=369，胶囊 right=355 → 溢出 14px，还越过了容器右边界
所以必须补一句，例如给按钮加 `overflow:hidden`、给内部 `[data-i18n]` span 加
`overflow:hidden; text-overflow:ellipsis`，或者干脆在窄屏下缩小 font-size / 只留 emoji。
（顺带：`overflow-x:visible` 之后 `-webkit-overflow-scrolling:touch` 和
`::-webkit-scrollbar{display:none}` 就成了死规则，可以一起清掉。）

【修法 (2) scrollIntoView：能用，但有个没提到的副作用】
实测调用后 `.home-category-tabs.scrollLeft` 从 0 变成 54.5（= maxScrollLeft 55），确实把 tab 滚进来了。
但 `scrollIntoView` 会**沿着所有可滚动祖先一路滚**，不只是那个 tab 条。
实测在 `document.scrollingElement.scrollTop = 400` 的状态下调用，
scrollTop 被改成了 393 —— 页面被竖向拽了一下。
而 syncIndicators 是从 pager 的 scroll 回调里调的（homeScreen.js:104），
也就是说：孩子把首页往下滚去够下面几行图标，然后横滑翻页，页面会自己往上跳一段。
（如果他滚得更远，跳得更多。）
建议改成直接设 scrollLeft，不碰任何祖先：
```js
const strip = document.querySelector('.home-category-tabs');
const el = document.querySelectorAll('.home-tab')[i];
if (strip && el) strip.scrollLeft = el.offsetLeft - (strip.clientWidth - el.offsetWidth) / 2;
```
另外原文引用的「踩坑记录第 11 条：这个容器没有 scroll-snap」这句本身查证属实——
scroll-snap 只加在 `.home-pager` 上（css/style.css 的 .home-pager 块），tab 条没有。

【推荐】优先用修法 (1) 并补 overflow 处理：它彻底消灭「有东西被切掉」这个观感，
而且不引入任何运行时逻辑，符合「改一个配置就生效」的偏好。
修法 (2) 只是让被切掉的东西滚进来，治标，还多一个竖向跳动的风险。

注意：改完 css/style.css 后按踩坑记录第 12 条 bump `sw.js` 的 `CACHE_NAME`，否则老设备看不到。

## 42. Google Analytics 用默认配置跑在儿童应用上，广告个性化信号没关，且上报了孩子看的具体视频标题和练的汉字

- **位置**：`index.html`:5
- **分类**：privacy

**孩子/家长会遇到什么**

一个 5-7 岁孩子在自家 iPad 上练字、看动画，这些行为（具体视频标题、具体练了哪个汉字、每个模块停留多少秒）会带着设备标识上传给 Google，并在默认配置下参与广告受众构建。即使只是家长自己看数据，也没必要开广告信号。

**建议修法**

一行配置的事：
```js
gtag('config', 'G-RCEWX2DDQQ', {
  anonymize_ip: true,
  allow_google_signals: false,
  allow_ad_personalization_signals: false
});
```
另建议把 video_name（视频标题）从上报里去掉，只留 video_id 或干脆只留计数——家长想知道的是「今天看了几个视频」，不需要把标题送给 Google。如果只是自用统计，更彻底的做法是去掉 GA，改成本地 localStorage 统计 + 已有的「📊 学习报告」模块。

**验证环节的补充/纠正**

**建议修法基本可行，但要去掉一个无效参数：**

```js
gtag('config', 'G-RCEWX2DDQQ', {
  allow_google_signals: false,
  allow_ad_personalization_signals: false,
  send_page_view: false        // 见下面第 2 点
});
```

1. **删掉 `anonymize_ip: true`** —— 这是 Universal Analytics 时代的参数，GA4 **永远强制匿名化 IP**，该参数被直接忽略。留着不会出错但是死配置，会误导以后的维护（让人以为「IP 已经处理过了」而不再核实其他项）。另两个参数 `allow_google_signals` / `allow_ad_personalization_signals` 在 GA4 里是有效的，设 false 只会丢失人口统计和再营销数据，**页面浏览、事件、时长报表全部照常工作**，不会引入新问题。

2. **顺手修一个同一位置的数据准确性 bug（原报告没提）**：`gtag('config', ...)` 默认 `send_page_view: true` 会自动发一次 page_view，而 js/analytics.js:123-128 的 `trackPageView()` 又手动发了第二次 —— 每次开应用 **page_view 都被记两遍**，家长看到的访问量是虚高一倍的。要么按上面加 `send_page_view: false`，要么删掉 analytics.js 里的 `trackPageView()`（二选一，别都做，否则一次都不记）。

3. **`page_location` 那条可以不管**：GA4 本来就会自动带 page_location，而且这个应用没有 hash 路由 / query 路由（全项目搜不到 `location.hash` / `pushState`），URL 恒为站点根地址，不含任何孩子的数据。这条属于原报告凑数的部分。

4. **`video_name` / `book_title` / `character` 是否要去掉，是家长的取舍而非 bug**：去掉后 GA 里就只剩「今天看了 3 个视频」，没法看「哪本绘本最受欢迎」。如果家长确实想要内容维度，更好的做法不是把它们发给 Google，而是走本项目已有的「📊 学习报告」（js/learningReport.js + localStorage）在本地统计 —— 这也更符合「离线优先」的硬约束。

5. **别加 cookie 同意横幅**。踩坑记录第 18 条已经明确「全英文的 Terms of Service / Privacy Policy 同意框给 5-7 岁孩子看等于功能不可用」，同样的道理适用于 GA 同意弹窗。上面这一行配置正是不打扰孩子的解法。

6. 严重度维持 **P2**，不上调：孩子端**完全没有可见故障**，这不是安全漏洞（数据是发给自己选的分析商，不是泄露给攻击者），而且「是否真的在建广告受众」取决于代码里看不到的 GA 后台属性设置。但也不该下调到 P3 —— 目标用户是儿童、站点公网可访问、修复成本一行。

**验证环节的补充/纠正**

修法方向正确且可行，但给的命令有两个坑，我实测过，照抄会得到不合规的图：

**坑 1：sips 能读 SVG（我实测通过），但不会自动缩放**
`sips -s format png icons/icon-192.svg --out icons/icon-180.png` 在这台 Mac 上确实成功了（新版 macOS ImageIO 已支持读 SVG），彩虹 emoji 也正常渲染出来了。但输出实测是 **192x192，不是 180x180**：
```
pixelWidth: 192   pixelHeight: 192   hasAlpha: yes
```
文件名叫 icon-180、HTML 里写 `sizes="180x180"`，实际却是 192——iOS 会自己缩放，不算致命，但属于自欺。要真出 180 必须加 `-z`：
`sips -s format png -z 180 180 ... `

**坑 2（更重要）：直接导出会带透明圆角，iOS 上会出黑角**
SVG 里是 `<rect width="192" height="192" rx="40" .../>`，导出的 PNG 四角是透明的（实测 `hasAlpha: yes`）。而 iOS 会**再叠加一次自己的圆角遮罩**，透明区域被合成到黑色上 → 图标四角出现黑色楔形。Apple 对 apple-touch-icon 的要求就是**满幅方图、不透明、不要自己切圆角**。

我实测了正确做法并确认有效：先把圆角去掉再导出，四角就被渐变填满、无透明区：
```bash
sed 's/rx="40"/rx="0"/' icons/icon-192.svg > /tmp/icon-flat.svg
sips -s format png -z 180 180 /tmp/icon-flat.svg --out icons/icon-180.png   # iOS
sips -s format png -z 512 512 /tmp/icon-flat.svg --out icons/icon-512.png   # Android/Chrome
sips -s format png -z 192 192 /tmp/icon-flat.svg --out icons/icon-192.png
```
（保留原 SVG 不动，只是导出时临时去圆角。）

**坑 3：sw.js 那条建议其实不必做，而且有风险**
原文建议「把新增的 PNG 加进 sw.js 的 urlsToCache」。我 grep 了 `sw.js`，`icon` 和 `manifest` 的命中数是 **0**——现有的 SVG 和 manifest.json 本来就不在 precache 列表里。而且主屏图标是「添加到主屏幕」那一刻走网络抓的，不经过 SW 离线路径，**加进去没收益**。反而按你自己踩坑记录 #14，`cache.addAll()` 只要一个 URL 404 整个 SW 安装就失败——多加几条只是多几个踩雷点。建议这条跳过。

**必须做的**：改了 index.html 就要按踩坑记录 #12 bump `sw.js` 的 `CACHE_NAME`（当前 `kids-learning-v69`），否则老设备上的 SW 一直返回旧 HTML，图标改了也到不了用户手上。

**顺带把 manifest 那条假 512 修掉**：
```json
"icons": [
  { "src": "icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
  { "src": "icons/icon-512.png", "sizes": "512x512", "type": "image/png" }
]
```
HTML 侧：
```html
<link rel="apple-touch-icon" sizes="180x180" href="icons/icon-180.png">
```
（apple-touch-icon 优先级高于 manifest icons，所以这一行是决定性的那一行。）

## 46. Service Worker 更新只监听 updatefound，不检查 registration.waiting —— 孩子错过一次更新提示后就再也收不到新版本

- **位置**：`js/app.js`:17
- **分类**：correctness

**孩子/家长会遇到什么**

这条和踩坑记录 #12「不 bump 版本号更新就到不了用户手上」是同一件事的下半段：版本号 bump 了，但更新照样到不了。典型场景——家长 push 了新版（比如 CI 更新了 data/videos.json），孩子打开 App 看到「🎉 发现新版本！」，没理它直接去玩，退出。第二天再打开，提示条不再出现，孩子看到的仍然是旧缓存里的旧视频列表/旧功能，而且再也不会自动恢复，除非家长手动去「我的信息 → 强制刷新」。iOS 上 PWA 常驻后台，这个状态可能持续很多天。

**建议修法**

在 register().then 里补一段：`if (registration.waiting && navigator.serviceWorker.controller) { newWorker = registration.waiting; showUpdateNotification(); }`，并把 `newWorker` 的赋值改成同时兼容 installing/waiting。

**验证环节的补充/纠正**

建议的修法可行，我已实测验证前提条件：在卡住的那次加载（LOAD-3）里，`register().then` 的回调**同步执行时** `registration.waiting` 就已经是 truthy 了（实测日志 `SW registered. controller=true installing=false waiting=true active=true`），不需要等待或轮询，所以直接在 .then 里判断是有效的。

两点补充：

1) 不要只在 register().then 里查一次。实测 LOAD-2（新版本刚下载那一次）在 .then 回调执行时 `installing=false waiting=false`——更新检查还没产生 worker，是几百毫秒后才 updatefound。所以 waiting 检查和现有的 updatefound 监听**必须两条都保留**，缺一不可，不能用 waiting 检查替换 updatefound。showUpdateNotification() 只是 classList.remove('hidden')，重复调用无副作用，不用担心两条路径都命中。

2) 更适合这个用户群的做法（建议优先于弹横幅）：目标用户是不识字的 5-7 岁孩子，「🎉 发现新版本！立即更新 ✕」这条横幅对他们本来就是不可读的，而且带一个 ✕ 会诱导孩子把更新永久关掉。既然 registerServiceWorker() 是在 DOMContentLoaded 里跑的（app.js:75-77），此刻孩子还没有任何进行中的操作（没画到一半的画布、没玩到一半的关卡），可以对 **waiting 分支直接静默应用**，不弹横幅：

   if (registration.waiting && navigator.serviceWorker.controller) {
     registration.waiting.postMessage({ type: 'SKIP_WAITING' });  // 走 sw.js:100-102，触发 controllerchange → app.js:41-46 自动 reload
   }

   这样是「冷启动瞬间自动完成更新」，孩子只会看到一次极快的白屏，不需要读任何字。而 updatefound 那条路径（用户正在使用中途下载好的新版本）保留现有横幅行为不变——那时候孩子可能正在画画，静默 reload 会丢失画布内容，不能自动应用。

   注意：静默分支必须只在 DOMContentLoaded 的首次注册时跑，不要放进任何会被重复调用的地方，否则有 reload 循环风险（controllerchange 里的 `refreshing` 标志 app.js:40-45 只防同一次页面生命周期内的重复，防不住跨 reload 的循环）。实测中 SKIP_WAITING 后 waiting 会变 null、新 SW 成为 controller，不会二次触发，逻辑上是收敛的。

3) `applyUpdate()`（app.js:66-72）在 newWorker 为 null 时只隐藏横幅的问题，如果按上面改了就自动消失了；若只做最小修法，记得把 waiting 分支里的 `newWorker = registration.waiting` 也赋上，否则横幅弹出来但「立即更新」按钮点了没反应，比不弹更糟。

5. 别忘了 bump sw.js 的 `CACHE_NAME`，否则老设备拿的还是缓存里的 app.js。

两个选择：(1) `navigateTo()` 里离开 timer 页时暂停（`if (currentPage === 'timer' && page !== 'timer') timerPaused = true;`）——但这跟「家长设定玩耍时长」的初衷冲突；(2) 更合适：保持后台运行，但在 `finishTimer()` 里先关掉当前打开的模块再弹，并把提示改成孩子能懂的：`document.querySelectorAll('[id$="-modal"]:not(.hidden)').forEach(m => m.classList.add('hidden'));`。另外 setInterval 每秒减 1 在 iOS 后台会被挂起，建议跟睡眠音乐一样改成基于 `Date.now()` 的结束时间戳。

原证据里有 3 处需要纠正，修法也要改：

1) 「盖在任何模块上面」是过头的说法。实测这些模块的根容器是 z-index 10000，弹窗是被压在下面、根本看不见：`.draw-smash-modal`（style.css:14854 区块，运行时读到 `draw-smash-modal z=10000 pos=fixed`，背景 rgba(0,0,0,0.9)）、`.ragdoll-robot-modal`（15307）、`.bp-fullscreen-modal`（18996）、`.pw-fullscreen-modal`（19267）。所以原文举的「正在玩画线砸怪兽」例子是错的——孩子只会听到声音，弹窗静静躺在游戏后面，等他退出游戏时才突然出现（其实更莫名其妙）。真正会被盖住的是 `#drawing-modal`（z=1000）、`#picture-book-modal`（z=1000）和所有 `.page` 模块（数学/中文/探索视频/拼图等，无 z-index），这部分我实测确认了。

2) iOS Safari 不支持 `navigator.vibrate`，app.js:1360-1362 的震动在目标设备上是空操作，别把它算进影响。

更安全的三步小改（都符合「改一处就生效」的偏好）：
a) 把 `.timer-finish-modal` 的 z-index 从 2000 提到 10001，保证在任何模块之上都可见可点——现在的不一致（有时盖住、有时藏在后面）比哪一种都糟。
b) 首页/顶栏加一个「⏰ 计时中 mm:ss」的常驻小标（updateTimerDisplay 里顺手写一个 span 即可），让孩子和家长知道这声音是哪来的；弹窗文案给个 data-i18n（index.html:576-578 的 OK 按钮「好的，我知道了 👋」现在是硬编码中文，没有 data-i18n，其他语言下不翻译）。
c) 把 timerSeconds 递减改成 `timerEndTime = Date.now() + timerSeconds*1000`，setInterval 里用 `Math.ceil((timerEndTime - Date.now())/1000)` 重算，并复用已有的 visibilitychange 思路（app.js:2562 的 handleVisibilityChange 就是现成范式）。这条能修掉 iOS 后台挂起导致计时不准的问题。
不建议采纳原文的方案(1)（离开页面就暂停）——那会让「家长设定玩耍时长」彻底失效。

孩子在家庭积分榜里往下滑记录列表，滑到底后继续滑，底下的首页跟着一起滚；关掉弹窗回到首页时页面停在一个奇怪的位置，「今日进度」卡片跑到屏幕中间。在 iOS 上这个穿透还会带出橡皮筋回弹，整个弹窗看起来在晃。签到提醒盖住模块的问题（已知）本质上也是这个——只要还有任何延时/异步触发的弹窗，同样的事就会再发生一次。

**建议修法**

加一个约 30 行的极小管理器（不动现有 36 个模块的结构，只在 open/close 里各加一行）：
```js
const ModalStack = {
  stack: [],
  open(id) {
    // 打开新的先关旧的（或按需允许叠加）
    const el = document.getElementById(id); if (!el) return;
    el.classList.remove('hidden');
    this.stack.push(id);
    document.body.classList.add('modal-open');
  },
  close(id) {
    const el = document.getElementById(id); if (el) el.classList.add('hidden');
    this.stack = this.stack.filter(x => x !== id);
    if (!this.stack.length) document.body.classList.remove('modal-open');
  }
};
```
配 `body.modal-open { overflow: hidden; position: fixed; width: 100%; }`（iOS 上需要记录/恢复 scrollY）。z-index 改成 CSS 变量分层：`--z-module: 1000; --z-result: 1500; --z-toast: 2000; --z-fullscreen: 3000;`。

**验证环节的补充/纠正**

建议的修法有三个会引入新问题的地方，照抄会踩坑：

1. **`--z-fullscreen: 3000` 是明确的回归**。全屏游戏/生日派对/魔法公园现在是 10000，就是为了压住 `#particles`(9999，style.css:33) 和 `.update-notification`(9999，style.css:8907)。降到 3000 之后，孩子玩画线砸怪兽时 Service Worker 的「立即更新」横幅和粒子层会浮在游戏画面上——这正是 14854 那段注释里说的"容易误触被弹出去"。要做 CSS 变量分层可以，但全屏档必须 >9999。

2. **"打开新的先关旧的"不能无脑做**。1100/1500/1600 那一层本来就是设计成叠在模块弹窗(1000)之上的完成弹窗/结算弹窗/成就弹窗，模块弹窗在下面是有意的。统一 open() 里关旧的会把这些全打碎。要做只能是白名单式的"同级互斥"。

3. **`body { position: fixed }` 这条别用**。body 现在是 `min-height: 100vh`（style.css:19-24），加 position:fixed 会塌掉布局；而且要在 118 处 `classList.remove('hidden')` 对应的所有 open/close 路径上正确存取 scrollY，漏一处孩子就被扔到页面顶部或半截位置——引入的 bug 大概率比修掉的多，跟"唯一维护者是家长、不接受重型重构"的约束也冲突。

**更小、对这个仓库更安全的做法**：iOS Safari 是尊重根元素 `overflow: hidden` 的，而且不像 body position:fixed 那样丢失滚动位置，不需要存取 scrollY。所以只要：
```css
html.modal-open { overflow: hidden; }
```
加一个十来行、不改任何现有模块结构的开关（比如在 body 上挂一个 MutationObserver 监听 `.hidden` 类变化，或者只在最容易漂的那几个入口手动加/减 class），就能把绝大部分穿透堵掉。

另外一条几乎零风险、可以先单独上的：给所有 fixed inset-0 的弹窗根加 `overscroll-behavior: contain`（iOS 16+ 支持），至少把 `.chore-tracker-modal` 这类自身可滚容器的滚动链断掉。注意它救不了 `.ai-chat-modal` 那种根元素 `overflow: visible` 的——那种得让根元素自己变成滚动容器（`overflow-y: auto` + `overscroll-behavior: contain`）才有效。

最后，如果只能改一处：在各模块 close 时补一句 `window.scrollTo(0, 0)`（或记录打开时的 scrollY 再还原），成本极低，直接消灭"关掉弹窗被丢在列表 1800px 处"这个最伤的症状，即使穿透本身还在。

## 50. 启动链路整段没有 try/catch，任一模块的 JSON.parse 失败就整页死；而且应用内没有任何重置入口，坏了就永远打不开

```js
function loadJSON(key, defaults) {
```

## 51. `I18n.t(key) || '中文'` 这个惯用法（120 处）是死代码，缺键时会漏出原始 key 而不是中文

- **位置**：`js/dailyCheckin.js`:88
- **分类**：footgun

**孩子/家长会遇到什么**

这是个定时炸弹：家长以后加任何新文案时照着现有风格写 `I18n.t('foo.bar') || '中文'`，只要忘了同步 7 个 locale，孩子看到的不是中文兜底，而是屏幕上一串「foo.bar」——和 pet.fedMessage 一模一样。因为写法看起来「有兜底」，问题在 code review 时极难发现。

**建议修法**

两步：
1) 批量把 `I18n.t('x') || 'y'` 改成 `I18n.t('x', 'y')`（t 的第二参数本来就是为这个设计的）。可以用一条 sed/正则一次改完 120 处，语义完全等价且更安全。
2) 加一个 CI 校验脚本（纯 node，无依赖）：加载 7 个 locale，扫全项目的 data-i18n 属性和 t('...') 调用，报出「任一 locale 缺失的键」并 exit 1。这一条能同时挡住本清单里 4 个 P1（park.*、math.range 那 14 个、pet.fedMessage、eb.* 缺 64 个）的再次发生。

**验证环节的补充/纠正**

严重度维持 P2（不上调也不下调）：今天除了 pet.fedMessage（已另计 P1）之外没有额外的线上可见破损，所以够不上 P1；但它已经**实际产出过一个上线 bug**、覆盖 124 个调用点、且项目里两种惯用法并存容易照抄，所以也不是 P3。

对建议修法的纠正：

**(a) "语义完全等价"这个说法是错的，别这么写进 commit message。** 改成两参形式恰恰是**改变行为**——这正是修复的目的。副作用要讲清楚：以后某个键缺失时，英语/日语/韩语用户看到的会从 `foo.bar` 变成一串中文，而不是英文。对这个家庭（主用户是中文家庭）是净收益，但要意识到它把"缺翻译"从**显性报错**变成了**静默降级**。所以第 (2) 步的 CI 校验不是可选项，是这个改法的前提。

**(b) 一条 sed 改完 124 处是不现实的，至少 4 处必须手工处理：**
- js/app.js:1597 / 1736 / 1936 —— 兜底是**数组**不是字符串字面量，正则 `\|\| '...'` 匹配不到；且这三处失败形态最恶劣（见上面第 7 点），建议单独手工改成 `I18n.t('calendar.months', [...])`。
- js/learningPet.js:927 —— 是 `(typeof I18n !== 'undefined' && I18n.t('pet.fedMessage')) || '...'` 守卫形式，多一层括号，正则同样漏。而且这处的**根本修法是把 `pet.fedMessage` 键补进 7 个 locale**，改成两参只是把"显示 key"降级成"显示中文"，治标不治本。
- 其余 120 处的字符串兜底里，我检查过没有反引号兜底、没有转义单引号、没有跨行的 `||`（我第一次 grep 出的 wrongQuestions.js 那 20 条跨行嫌疑是正则回溯造成的假阳性，实际都是单行），所以那 120 处正则批量替换是安全的。包在括号里的形如 `(I18n.t('x') || 'y').replace(...)` 替换后变成 `(I18n.t('x','y')).replace(...)`，多余括号无害。

**(c) 一个真实的新坑：locale 里的空字符串会被两参形式吃掉。** t() 用的是 `if (translation) return translation`（truthy 判断，不是 `!== undefined`），所以值为 `''` 的翻译会被当成缺失。我实测项目里现有 7 个空值翻译，涉及 2 个键：`birthday.day`（en/es/fr 为 `''`）和 `tooth.thTooth`（en/es/de/fr 为 `''`）。这两个键**已经**在用两参形式，后果现在就能看到：js/birthdayParty.js:290 `\`${m}${t('birthday.month','月')}${d}${t('birthday.day','日')}\`` 对英语用户渲染出的是 "7月28日" 而不是 "7/28"——中文字漏进英文界面。虽然这两个键不在本条的 124 处里，但如果批量改成两参，以后任何"故意留空"的翻译都会漏中文。正解是顺手把 i18n.js:53 和 :58 的 truthy 判断改成 `!== undefined` 判断，让"故意留空"和"没定义"区分开。这个改动 2 行，风险低，建议和 (a) 一起做。

**(d) 优先级建议：先做第 (2) 步的 CI 校验脚本，再做第 (1) 步的批量替换。** 校验脚本才是真正抓 bug 的那一半（能一次性抓出 pet.fedMessage 以及清单里另外几条缺键 P1）；批量替换只是把失败形态从"露 key"降级成"露错语言的文案"。脚本本身很好写：node 里用 `new Function('I18n', src)` 就能直接 eval 那 7 个 locale 文件（我这次验证就是这么做的，无任何依赖），然后扫全项目的 `data-i18n=` 属性和 `t('...')` 调用做差集。注意脚本要同时覆盖 `I18n.t(` 和各文件里的局部 `t(` 别名两种写法。

我实测确认：`grep -n "addEventListener('resize'|onresize|orientationchange|visualViewport" js/drawSmash.js js/ragdollRobot.js` **零命中**。`_initCanvasSize()` 每关只在 `requestAnimationFrame` 里跑一次（drawSmash.js:253-256），算出的 `this.canvasScale` 之后被 `_toLogical()`（drawSmash.js:296-301）用来做「屏幕坐标→逻辑坐标」换算。

`dvh` 是**动态**视口，会随工具栏收起/展开变化。如果游戏在工具栏收起状态开始（box=741），玩到一半工具栏弹出（box→659），wrapper 变矮，而 `#ds-canvas { max-height: 100% }`（style.css:15176）会把画布元素压扁，但 `canvasScale` 还是旧值 → 触摸坐标换算错位，孩子画的线会跑偏。这比原来的问题更糟。

`svh` 恒等于「工具栏展开时」的小视口，值不变，不会中途重排，也保证不被遮挡。PWA 独立模式下 svh == dvh == lvh，没有副作用（只是 Safari 里底部会多出 82px 黑边，纯观感）。

建议：
```css
#draw-smash-game { height: 100vh; height: 100svh; }
#rr-game        { height: 100vh; height: 100svh; }
```
两处的 `height` 都不带 `!important`（只有 padding 和 min-height 带），所以第二条声明能正常覆盖，老 Safari 会忽略 svh 落回 vh，兜底成立。

如果坚持用 `dvh`，就必须同时给两个游戏加上 resize/orientationchange 监听去重新调用 `_initCanvasSize()`，那就不是一行 CSS 的改动了，跟「改一个配置就生效」的偏好冲突。

报告里顺带提的 style.css:22 和 194 两处 `min-height: 100vh`（我确认行号准确）确实只是多 82px 空滚动，危害更小，可以一起顺手改，也可以完全不管。

## 65. 拼图拖动没处理 touchcancel，被系统手势打断后碎片会永久卡在屏幕上

- **位置**：`js/puzzle.js`:434
- **分类**：touch-interaction

**孩子/家长会遇到什么**

孩子拖着拼图碎片时手机弹了条微信通知（或者另一只手蹭到屏幕），碎片就以 `position:fixed; z-index:1000` 定在手指最后停留的位置不动了——挡住底下的拼图格子，再点它也没反应（`draggedPieceElement` 还占着），孩子只能退出重拼，之前拼好的全没了。

**建议修法**

复用现有的收尾逻辑即可：
```js
piece.addEventListener('touchcancel', handleTouchEnd, { passive: false });
```
但 `handleTouchEnd` 开头用的是 `event.changedTouches[0]`，touchcancel 时也有值，逻辑能跑通；保险起见在函数开头加 `if (!event.changedTouches || !event.changedTouches.length) { /* 只做样式复位 */ }` 分支。同理 drawing.js:207、drawSmash.js:281、ragdollRobot.js:422 的 pointer 系列都缺 `pointercancel`，建议一并补上（把 pointerup 的处理函数直接复用）。

**验证环节的补充/纠正**

建议的一行修法有副作用，不要直接照抄。

`piece.addEventListener('touchcancel', handleTouchEnd)` 会把「取消」当成「放下」：handleTouchEnd:482-491 拿 changedTouches[0] 去 getSlotUnderTouch 并调用 placePiece。touchcancel 的 changedTouches 按规范是非空的，所以逻辑确实跑得通——但后果是，如果来电打断时手指正悬在某个槽位上方，碎片会被**自动放进去**，放错还会触发 585 行的抖动动画和 586 行的 'wrong' 音效。孩子没做任何操作却被判了一次错，比留个幽灵更糟。

正确做法是单独写一个只复位、不放置的 handler：
```js
function handleTouchCancel() {
  if (!draggedPieceElement) return;
  document.querySelectorAll('.puzzle-slot').forEach(s => s.classList.remove('drag-over'));
  draggedPieceElement.classList.remove('dragging');
  draggedPieceElement.style.position = '';
  draggedPieceElement.style.left = '';
  draggedPieceElement.style.top = '';
  draggedPieceElement.style.zIndex = '';
  draggedPieceElement = null;
  draggedPiece = null;
}
piece.addEventListener('touchcancel', handleTouchCancel, { passive: false });
```
（也可以更省事：直接 `renderPuzzlePieces(puzzlePieces.filter(p => !p.placed))`，反正它会重建整个碎片区，顺便把状态清干净。）

另外，原报告附带的「drawing.js:207、drawSmash.js:281、ragdollRobot.js:422 同理缺 pointercancel，建议一并补上」是**错的，这三处已经覆盖了**：
- js/drawing.js:207-208 同时绑了 pointerup 和 `pointerleave` → 都指向 stopDrawing()
- js/drawSmash.js:285-286 和 js/ragdollRobot.js:425-426 都是 `onpointerup` + `onpointerleave` 指向同一个 `_onPointerUp`

Pointer Events 规范规定 pointercancel 之后 UA 必须依次派发 pointerout 和 pointerleave，所以这三个模块的 pointerleave 分支本来就会兜住取消场景。puzzle.js 的问题恰恰在于它用的是 touch 事件族，而 touch 没有 pointerleave 这种等价兜底——这是它唯一特殊的地方，不要顺手去改那三个文件。

**验证环节的补充/纠正**

修法方向对，但「按需给 createParticles 加 emoji/count 参数」这一步有坑，别照做：

1. 【会引入新 bug】RewardSystem.createParticles 当前签名是 0 参（rewards.js:286），但现有调用点已经有两种位置参数用法：
   - `RewardSystem.createParticles()` — dailyCheckin.js:314、puzzle.js:647、achievements.js:152 等十几处
   - `RewardSystem.createParticles(e.clientX, e.clientY)` — reactionGames.js:477/674/828/950、logicGames.js:750/897（现在被忽略，无害）
   如果按建议改成 `createParticles(emoji, count)`，reactionGames 那 6 处会变成 emoji=413（clientX 数值）、count=super 大的 clientY，粒子上会显示数字、数量也会失控。**要么保持 0 参不动，要么改成 options 对象** `createParticles({emoji, count})` 并对非对象入参走默认值。
   最省事的做法就是 writing.js:393 直接写 `if (typeof RewardSystem !== 'undefined') RewardSystem.createParticles();`（跟 toothFairy.js:514 保持一致），接受它放 30 个随机 emoji 而不是 10 颗 ⭐——对 5-7 岁孩子来说更热闹反而更好。

2. 【可行性已验证】
   - `#particles` 容器存在（index.html:24），createParticles 不会因为找不到容器而抛。
   - 加载顺序没问题：rewards.js 在 index.html:2854，aiChat.js:2866，writing.js:2870，RewardSystem 先定义。
   - RewardSystem.playSound 支持 'reward' 和 'correct'（rewards.js:337 / 343），且整体包在 try/catch 里静默失败，改过去安全。
